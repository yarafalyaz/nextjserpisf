## FINDING 1 — IDOR (HIGH)
**File:** src/actions/inventory.actions.ts  
**Severity:** HIGH  
**Risk:** Any user with permission `edit_stock_adjustments` can process/update/delete ANY adjustment by ID, regardless of creator, warehouse, or scope.

**How:**
- `processStockAdjustment(adjustmentId: number)` → bare int param, no ownership/scope check
- `receiveInventoryTransfer(transferId: number)` → same
- `completeMaterialIssue(issueId: number)` → same
- `deleteStockAdjustment(id: number)` → same
- `updateStockAdjustment(id, formData)` → same
- All update actions follow same pattern

`requirePermission()` only checks the permission NAME exists on user's role. It never validates that the target record belongs to the user's warehouse/org unit. No tenant/ownership filter in any WHERE clause.

**Example:** User A (Warehouse 1) calls `processStockAdjustment(42)` where adjustment #42 belongs to Warehouse 2 → succeeds if user has `edit_stock_adjustments`, even though they shouldn't access WH2 stock.

**Fix:** Add warehouse/creator ownership check before processing, or include WHERE clause scoped to user's accessible warehouses.

## FINDING 2 — TOCTOU Race in updateStockAdjustment (MEDIUM)
**File:** src/actions/inventory.actions.ts (line 630–686)  
**Severity:** MEDIUM  
**Risk:** Concurrent `processStockAdjustment` and `updateStockAdjustment` can corrupt data.

**How:**
```
updateStockAdjustment() {
  const adj = findUniqueOrThrow()  // reads status = "draft"  ← T1
  if (adj.status !== "draft") throw
  // ← race window: processStockAdjustment claims & processes here (T2)
  $transaction(tx => {
    tx.stockAdjustmentItem.deleteMany(...)  // deletes items of now-processed adj
    tx.stockAdjustment.update({ items: { create: ... } })  // re-creates with new values
  })
}
```
`processStockAdjustment` uses atomic `updateMany(where:{status:"draft"} → "processing")` which protects itself. But `updateStockAdjustment` only reads status then proceeds without claiming; a concurrent process call can change status between the read and the tx. The update then silently modifies already-processed records.

**Other update functions affected:** `updateMaterialIssue` (line 688), `updateInventoryTransfer` (line 737) — same pattern.

**Fix:** Use same atomic claim pattern: `updateMany(where:{id, status:"draft"}, data:{status:"locked_update"})` before the update transaction.

## FINDING 3 — Missing actualQty >= 0 Validation (MEDIUM)
**File:** src/actions/inventory.actions.ts (line 29–31, 643–645) + src/lib/hooks/stock-adjustment.hook.ts (line 59)  
**Severity:** MEDIUM  
**Risk:** User can set `newQty` (actualQty) to negative values → stock adjustment drives `qty_on_hand` negative.

**How:**
- `createStockAdjustment`: parses items JSON, filters `itemId > 0` but does NOT validate `newQty >= 0`
- `updateStockAdjustment`: same, no `newQty >= 0` guard
- Hook `onStockAdjustmentProcessed`: `const actualQty = Number(item.actualQty)` — no range check
- Schema: `Item.qtyOnHand` is `Decimal(15,2)` with no CHECK constraint — allows negative values

A user could submit `newQty: -100`. The hook computes `qtyDiff = -100 - liveQty` (even more negative), converges `qty_on_hand` to -100. Schema allows it.

**Fix:** Add Zod validation `z.coerce.number().min(0)` for actualQty/newQty in the schema or at action level. Add DB CHECK constraint or application-level guard in hook.

## FINDING 4 — Negative Stock Bypass: INVENTORY SERVICE Paths (LOW)
**Severity:** LOW (already mitigated)  
**Risk:** Well-guarded, negative stock prevented.

**Mitigations verified:**
1. `inventory.service.ts handleOut()` (line 141–148): atomic `UPDATE items SET qty_on_hand = qty_on_hand - ${qty} WHERE id = ... AND qty_on_hand >= ${qty}` — DB-level guard. Returns 0 → throws "Concurrent stock modification detected".
2. `inventory-fifo.ts consumeFifoLayers()` (line 74–83): shortfall guard throws if available layers < requested qty. Uses `FOR UPDATE` row lock (line 66–71) so reads latest committed remaining.
3. Stock adjustment hook converges to actualQty (safe by design: `qty_on_hand = liveQty + (actualQty - liveQty) = actualQty`). Provided actualQty >= 0 (see Finding 3).

**No caller passes `allowShortfall=true`** in the audited code paths.

## FINDING 5 — Race Condition Protection (LOW)
**Severity:** LOW (well-mitigated)  
**Risk:** Existing race condition defenses are robust with one process-stuck edge case.

**Mitigations verified:**
1. **Atomic claim pattern** in all process functions: `updateMany(WHERE status="draft", data: {status:"processing"})` — only one concurrent caller wins.
2. **FOR UPDATE row locking** inside all hook transactions: items, inventory_layers, and source documents are locked before any write.
3. **Serializable isolation** in `inventory.service.ts postMove()` — strongest isolation level.
4. **Idempotency guards** inside hooks: check `findFirst(stockMove WHERE referenceType+Id)` before creating — returns silently if moves exist.
5. **Lock-before-check ordering**: hooks acquire `FOR UPDATE` on the source document BEFORE the idempotency check — prevents two waiters from both seeing no moves.

**Edge case:** If a hook throws mid-transaction (e.g., network blip during FIFO consume), the transaction rolls back (no partial state). BUT the action's status claim (`draft → processing`) is OUTSIDE the hook's transaction. If the hook throws:
- Action catches → returns `{success:false, error:...}`
- Status remains "processing" — document is **stuck**
- No retry logic or auto-revert to "draft"

Same for: `processInventoryTransfer`, `receiveInventoryTransfer`, `completeMaterialIssue`,
`createSalesReturn`, `completeSalesReturn`, `postSalesInvoice`, `confirmGoodsReceipt`.

**Fix:** Wrap the status claim + hook call in a try-catch with fallback `update({status:"draft"})` on failure, or include the status claim inside the hook's transaction.

## FINDING 6 — No Row-Level Access Control (Single Tenant, but No Warehouse Scope) (INFO)
**Severity:** INFO  
**Risk:** No ownership/creator/warehouse scope checks in any action. Every action uses bare ID from client.

All server actions accept `(id: number)` or `(transferId: number)` directly from the client. No validation that:
- The adjustment/transfer belongs to user's warehouse
- The user created the document
- The document's warehouse is in user's accessible list

This is an architectural gap — RBAC (Role-Based Access Control) is implemented, but not ACL (Access Control List). If the app ever needs multi-warehouse access restrictions, every action needs an ownership/scope filter.
