# PRD — ERP Custom Fabrikasi Offroad Berbasis Laravel

**Versi:** 1.4 — kontrak API seluruh modul untuk web/Android, desain web responsif, quick add popup, dan katalog tipe/konfigurasi kendaraan  
**Tanggal:** 4 Oktober 2026  
**Status:** spesifikasi target; bukan klaim fitur sudah tersedia atau kebijakan akuntansi sudah disetujui.  
**Pemilik keputusan bisnis:** owner bengkel. Kebijakan akuntansi, pajak, dan payroll disahkan penanggung jawab finance bersama profesional yang berwenang.

## 1. Tujuan, batas kelengkapan, dan acuan

Membangun ERP untuk bengkel custom/fabrikasi offroad yang menghubungkan pelanggan, kendaraan, desain, penawaran, pembelian marketplace, gudang, fabrikasi, pemasangan, tenaga kerja, penagihan, akuntansi, dan layanan purnajual.

Masalah utama:

1. SKU yang sama dibeli berulang dengan harga berbeda, baik dari toko yang sama maupun toko lain. Harga listing murah belum tentu biaya perolehan termurah setelah ongkir, diskon, pajak, dan biaya platform.
2. Material, komponen, tenaga kerja, subkontrak, dan biaya mesin belum tentu tercatat lengkap per kendaraan/pekerjaan; margin penawaran dapat berbeda jauh dari laba aktual.
3. Pembayaran di muka, escrow marketplace, penerimaan parsial, retur, refund, dan tagihan terpisah membuat kas, persediaan, dan utang sulit direkonsiliasi.
4. Owner membutuhkan laporan keuangan rinci dengan jejak dari angka ringkasan ke jurnal, transaksi, bukti, lot pembelian, dan pekerjaan yang menggunakannya.

**Definisi “full fitur”:** seluruh kebutuhan wajib bernomor dalam dokumen ini selesai secara end-to-end, termasuk pengecualian, otorisasi, laporan, pembatalan, dan kriteria penerimaannya. Tidak berarti semua fitur semua ERP di dunia. Tambahan kebutuhan dicatat sebagai perubahan ruang lingkup, bukan diasumsikan telah tercakup.

Acuan:

- `docs/prd.md`: baseline cakupan ERP dan aturan penting sistem lama, bukan desain Laravel.
- `docs/prd-hpp-landed-cost.md`: referensi masalah landed cost; bagian yang berstatus defer bukan perilaku selesai.
- `docs/audit-rbac-2026-09-29.md`: referensi risiko ketidaksamaan izin UI, endpoint, dan seed.
- [Kontrak API ERP v1](kontrak-api-erp-v1.md): kontrak target autentikasi, resource, aksi bisnis, payload, kesalahan, dan laporan seluruh MOD-01–14 untuk web serta Android.
- [Spesifikasi web dan quick add](spesifikasi-web-quick-add.md): sistem visual, interaksi layar, matriks field dan popup tambah data referensi.
- Dokumen ini mendefinisikan target produk baru. Perubahan terhadap baseline ditandai di §22; penerapannya memerlukan persetujuan, tidak boleh diam-diam mengubah data historis.

## 3. Profil usaha dan asumsi rancangan

Keputusan dasar rancangan, belum merupakan hasil wawancara operasional:

- Satu badan usaha dengan banyak cabang, gudang, rekening, dan pusat biaya. Hak akses dibatasi per cabang/gudang; konsolidasi antar-badan-usaha tidak termasuk baseline ini.
- IDR sebagai mata uang pembukuan; zona waktu operasional Asia/Jakarta; awal tahun fiskal dapat diatur. Pembelian valuta asing didukung dengan kurs transaksi, pelunasan, dan penilaian saldo moneter akhir periode.
- Akuntansi akrual, double-entry, persediaan perpetual, metode FIFO. Tidak ada penggantian metode costing di tengah periode.
- Model usaha mencakup jasa pemasangan, fabrikasi pesanan, penjualan spare part, produksi barang standar untuk stok, dan pekerjaan subkontrak.
- Barang milik pelanggan dan kendaraan titipan dicatat sebagai custody, bukan otomatis aset/persediaan bengkel.
- Barang bernilai stok, jasa, consumable, aset tetap, dan barang titipan adalah jenis berbeda dengan perlakuan akuntansi eksplisit.
- Aplikasi web responsif desktop/tablet/ponsel; transaksi posting membutuhkan koneksi. Aplikasi native/offline bukan syarat baseline.
- Integrasi langsung marketplace bergantung izin dan API resmi. Pencatatan manual serta impor terverifikasi wajib berfungsi tanpa API tersebut.

**SEC-01:** permission per aksi: lihat, tambah, ubah draft, ajukan, setujui, posting, reverse, ekspor, lihat biaya, lihat margin, dan tutup/buka periode. Backend selalu memeriksa izin dan cakupan record; menyembunyikan tombol saja tidak cukup.

**SEC-03:** pembuat dan penyetuju berbeda untuk transaksi sensitif. Pengecualian usaha kecil harus dikonfigurasi eksplisit dan masuk laporan audit, bukan bypass tersembunyi.

HR/finance mendapat hak terpisah untuk lihat/ubah/verifikasi/ekspor setiap kelompok data sensitif. Nomor identitas/rekening dimasking pada daftar, notifikasi dan log; nilai lengkap serta file identitas hanya lewat akses terlindungi. Perubahan profil sensitif diajukan untuk verifikasi, bukan langsung mengganti rekening pembayaran.

## 6. Master data dan kendaraan

### 6.1 Barang, satuan, dan vendor

**MD-01 — Identitas barang:** SKU internal unik; nama/deskripsi; merek; part number OEM/aftermarket; kategori; foto; spesifikasi material, grade, dimensi; berat/volume; kompatibilitas kendaraan; barcode; tracking lot/serial; min/max stock dan reorder point.

**MD-02 — Harga:** harga master hanya referensi penawaran/anggaran. Simpan daftar harga pemasok bertanggal, last purchase price, last landed cost, histori dan rentang harga sebagai informasi terpisah. Mengubah master tidak mengubah nilai stok atau transaksi posted.

**MD-03 — Satuan:** satuan dasar per SKU; alternatif dan konversi per barang, misalnya 1 batang = 6 meter, 1 box = 20 pcs. Faktor disalin ke baris transaksi agar perubahan master tidak mengubah histori. Konversi kg-ke-meter hanya jika faktor material/dimensi terdefinisi; bukan konversi global.

**MD-04 — Pemasok:** identitas legal, nama toko, platform, URL/ID toko, rekening tervalidasi, kontak, NPWP bila tersedia, syarat bayar, rating internal, lead time, histori masalah. Penjual, platform, penerbit invoice, dan penerima pembayaran dapat berbeda dan harus dicatat terpisah.

**MD-05 — Mapping listing:** banyak listing/toko dapat merujuk satu SKU internal. Variasi ukuran/grade/kompatibilitas yang berbeda tidak digabung hanya karena namanya mirip. Mapping baru membutuhkan verifikasi; simpan snapshot judul, varian, harga, dan bukti transaksi.

**MD-06 — Master merek dan model barang:** merek dikelola sebagai master berkode unik, bukan teks bebas per transaksi; nama, alias pencarian dan status aktif. Model/seri berada di bawah merek, sedangkan varian SKU memuat atribut pembeda seperti ukuran, kapasitas atau part number. Barang custom/tanpa merek menggunakan penanda eksplisit, bukan diberi merek fiktif. Merek yang telah dipakai hanya dapat dinonaktifkan, tidak dihapus hingga memutus histori. Merek barang dan merek kendaraan mempunyai konteks terpisah; kesamaan nama tidak otomatis menyamakan keduanya.

**MD-07 — Master tipe barang:** pisahkan (a) kategori/subkategori untuk pengelompokan, (b) tipe/jenis teknis seperti winch, shock absorber, pipa atau plat, (c) merek/model/varian, dan (d) jenis perlakuan stok/akuntansi seperti bahan baku, komponen beli, barang jadi, consumable, jasa atau aset. Master tipe memiliki kode, nama, atribut teknis wajib, status aktif dan kategori yang sesuai. Status kepemilikan/titipan adalah dimensi tersendiri, bukan alasan mengganti jenis teknis barang. Contoh: kategori recovery → tipe winch → merek tertentu → model tertentu → varian kapasitas 12.000 lb → SKU unik. Form barang, pembelian, penjualan, pencarian, filter dan laporan memakai master yang sama; perubahan klasifikasi tidak menghitung ulang transaksi posted.

### 6.2 Kendaraan dan aset pelanggan

**VEH-01:** pelanggan dapat memiliki banyak kendaraan. Setiap unit menyimpan merek/model/generasi atau seri pasar/varian, konfigurasi pabrik yang terverifikasi, tahun produksi/model year, nomor polisi, VIN/nomor rangka bila ada, nomor/kode mesin, odometer, konfigurasi aktual suspensi/ban/drivetrain, modifikasi terdahulu, dan histori servis. Identitas unit tidak cukup berupa teks “Hilux”; katalog serta hubungan konfigurasi mengikuti VEH-04–08.

**VEH-02:** check-in dengan foto kondisi, kerusakan awal, tingkat isi bahan bakar (misalnya seperempat tangki, bukan jenis bensin/diesel pada katalog), perlengkapan titipan, keluhan, dan persetujuan pelanggan. **Check-in tidak dianggap lengkap tanpa checklist inspeksi awal (`VEH-02A`) yang disetujui pelanggan; WO tidak dirilis sebelum checklist awal lengkap.** Check-out mencatat hasil QC, barang yang dikembalikan, dokumen serah terima, dan penerima.

**VEH-02A — Checklist inspeksi awal sebelum pekerjaan dimulai (pre-work inspection):** sebelum kendaraan dikerjakan, bengkel menyelesaikan **checklist inspeksi awal bertanda tangan** yang memuat: identitas unit (plat/VIN/odometer), lingkup pemeriksaan sesuai pekerjaan yang diminta (body, mesin, kelistrikan, kaki-kaki, interior, ban, rem, lampu, kebocoran), item bercentang baik/tidak/tidak diperiksa, **daftar cacat atau kerusakan awal** dengan foto bertanggal, kondisi ban/aki/lampu, jumlah BBM, kelengkapan yang dititipkan, serta keluhan pelanggan. Checklist ini dihasilkan dari **master checklist ber-versi per jenis pekerjaan** (`FAB-10`), sehingga daftar periksa konsisten dan dapat diaudit.

Item dengan status "tidak diperiksa" wajib beralasan, bukan dikosongkan. Cacat yang sudah ada sebelum pekerjaan dicatat sebagai **kondisi awal** dan disalin sebagai pembanding pada inspeksi akhir (`FAB-13`); tanpa catatan ini, kerusakan yang muncul kemudian tidak dapat dibuktikan bukan dari pekerjaan bengkel maupun sebaliknya. Checklist awal **harus disetujui/ditandatangani pelanggan atau perwakilannya sebelum pekerjaan diserahkan ke lantai produksi**; bila pelanggan menolak menandatangani, itu dicatat sebagai pengecualian yang perlu persetujuan berizin, bukan dianggap setuju. Isi checklist menaut ke estimasi/penawaran (`SAL-01`, `SAL-02`) sehingga pekerjaan yang diusulkan berasal dari temuan yang benar. Menambah cacat baru ke dokumen setelah disetujui tidak boleh senyap; revisi bertanggal dengan alasan. Checklist awal tidak boleh dihapus atau ditimpa untuk menyembunyikan kerusakan yang tidak tercatat.

**Kebijakan tanda tangan (disahkan owner/kepala bengkel):** **tanda tangan digital sudah diizinkan dan setara dengan tanda tangan basah** untuk checklist inspeksi awal, checklist inspeksi akhir (`FAB-13`), surat jalan keluar (`SAL-13`), dan serah terima. Tanda tangan digital tidak boleh berupa gambar tanda tangan yang ditempel bebas; harus terikat pada identitas penanda tangan, waktu, dan isi dokumen yang disnapshot, dengan jejak audit `signed_by`, `signed_at`, `document_version`, dan `evidence_id`. Ini memungkinkan inspeksi berjalan tanpa kehadiran fisik pelanggan (misalnya unit dikirim lewat ekspedisi). Hanya format tanda tangan pelanggan yang bersifat rahasia/pribadi yang tetap perlu kehati-hatian retensi tersendiri; substansi persetujuan tidak berubah.

**VEH-02B — Karo: unit penampung sementara dan penguncian alat:** karo adalah **unit penampung sementara** yang menahan satu atau beberapa **alat** selama pengerjaan berlangsung. Bentuk fisik karo tidak dikunci oleh sistem: dapat berupa kendaraan pelanggan yang dititipkan, unit yang disepakati, rak/box, atau wadah lain yang dipakai bengkel; yang penting perannya, yaitu menampung alat. Selama alat terpasang/dititipkan pada karo, **alat tidak dapat dialokasikan** ke job atau karo lain; karo praktis "mengunci" alat sampai alat dilepas kembali. Karena itu, karo dicatat sebagai relasi eksplisit antara **karo, job/WO, dan alat yang ditampung**, bukan sekadar catatan bebas di kartu job.

Data karo: nomor karo berpola `KRO-` mengikuti DocumentSequence (`KRO-2026-0001`), tanggal alat dititipkan/dipasang, tanggal karo masuk/keluar, identitas unit penampung dan pemilik/asosiasinya (pelanggan, bengkel, atau vendor) bila berlaku, job/WO terkait, **daftar alat yang ditampung beserta nomor seri**, petugas penempatan, foto penempatan, kondisi alat saat dititipkan, serta kondisi karo saat alat dilepas. Alat yang sedang tertahan di karo **tidak boleh dialokasikan ke job lain** dan statusnya harus terlihat sebagai "tertahan di karo" sampai dilepas. Untuk pemakaian berulang, gunakan **nomor seri/alokasi alat** agar dua karo berbeda tidak dianggap menahan alat yang sama. Istilah "karo" tetap dipakai sesuai kebiasaan operasional bengkel; substansi aturannya berlaku umum untuk semua jenis unit penampung.

**Karo tidak berbiaya tambahan sampai alat kembali.** Selama alat belum dilepas/dikembalikan, penggantian atau perbaikan karo yang diperlukan **tidak dikenakan biaya tambahan kepada pelanggan** dan tidak boleh menjadi penagihan baru; ini menutup celah lama ketika karo tambahan/perpanjangan dianggap biaya. Setelah alat kembali, aturan karo berlanjut (perpanjangan/pemakaian berikutnya) mengikuti kebijakan yang disahkan owner (`FAB-14`). Karo tidak boleh dijadikan jalan memindahkan alat dari pemiliknya atau menahan unit pelanggan di luar kesepakatan.

**VEH-03:** barang bawaan pelanggan diberi identitas, qty, kondisi dan lokasi custody. Pemakaian/kerusakan/pengembaliannya tercatat tanpa membentuk HPP pembelian bengkel. Material milik bengkel yang dipasang tetap memiliki biaya normal.

**VEH-04 — Hierarki tipe mobil:** merek kendaraan → model → generasi/seri pasar → varian/trim memakai master terpisah dengan ID permanen, kode, nama, alias pencarian, parent yang sah, status aktif dan bukti sumber. Nama dagang bisa berbeda antar pasar dan tahun; generasi teknis dapat menyimpan kode platform/chassis terpisah dari nama pemasaran. Merek/model barang MD-06 tidak menjadi master kendaraan yang sama. Hilux adalah contoh model Toyota; label Revo, Rocco dan Travo dari kebutuhan pengguna wajib dapat dicatat pada tingkat seri/generasi atau trim yang benar setelah verifikasi katalog pasar/tahun, bukan dianggap semua nama setara atau kombinasi pasti tersedia. Alias “tipe” pada pencarian boleh menemukan nama tersebut tanpa menghilangkan klasifikasinya.

**VEH-05 — Konfigurasi kendaraan yang valid:** satu konfigurasi pabrik mengikat generasi/seri, varian, pasar/negara, rentang model year, bentuk bodi/kabin, platform/chassis, mesin dan penggerak. Dukung single/extra/double cab bila relevan. Mesin menyimpan kode, kapasitas cc sebagai angka dan jenis bahan bakar terpisah: bensin, diesel/solar, hybrid (beserta bahan bakar mesin pembakaran), plug-in hybrid atau listrik sesuai katalog. Transmisi menyimpan manual/otomatis/CVT/jenis lain yang terverifikasi dan jumlah percepatan bila diketahui; penggerak membedakan 4×2, 4×4 dan AWD sesuai spesifikasi, bukan satu flag “offroad”. Tidak membentuk seluruh kombinasi dari dropdown secara otomatis. Setiap konfigurasi yang dapat dipilih harus disahkan petugas master/engineering dengan referensi sumber dan masa berlaku; data belum diketahui bernilai null dengan status belum terverifikasi, bukan isi default palsu. Tahun produksi unit, model year dan tahun registrasi adalah field berbeda.

**VEH-06 — Unit aktual dan histori:** kendaraan pelanggan menunjuk configuration ID/version; konfigurasi pabrik disnapshot pada quotation/job/inspeksi yang disahkan. Engine swap, perubahan transmisi/penggerak, lift kit, ukuran ban, wheelbase atau modifikasi mounting dicatat sebagai perubahan aktual bertanggal dengan bukti/inspeksi, tidak mengubah master pabrik bagi seluruh kendaraan sejenis. Unit dengan tipe belum lengkap boleh disimpan sebagai draft untuk identifikasi, tetapi release pekerjaan/pemilihan komponen yang memerlukan fitment harus menunggu verifikasi teknis. Perubahan tipe unit tidak menimpa BOM/job yang sudah disetujui; revisi terkait mengikuti change order dan approval.

**VEH-07 — Kompatibilitas part, paket dan BOM:** relasi fitment dapat mengaitkan SKU/paket/revisi BOM ke konfigurasi kendaraan atau aturan cakupan yang disahkan (generasi, rentang tahun, pasar, mesin/bahan bakar, transmisi, penggerak, bodi/kabin serta syarat modifikasi). Hasil pengecekan adalah `compatible`, `incompatible`, atau `unknown`, dengan sumber, versi dan alasan. `unknown`/field kosong bukan berarti universal fit. Part yang cocok untuk satu Hilux tidak otomatis cocok untuk semua Hilux Revo/Rocco/Travo, bensin/diesel, 4×2/4×4 atau semua kabin. Komponen universal hanya dianggap demikian bila ada cakupan universal eksplisit yang disahkan; kondisi modifikasi aktual tetap diperiksa. Pengecualian/custom fabrication membutuhkan persetujuan engineering, alasan dan revisi desain/QC, bukan pengguna menekan “tetap pilih” tanpa kewenangan.

**VEH-08 — API, pencarian dan quick add bertingkat:** pencarian kendaraan/katalog mendukung kode/nama/alias, merek, model, generasi/seri, varian, pasar, tahun, mesin, bahan bakar, transmisi, bodi dan penggerak. Web/Android memakai resource katalog dan validasi parent/configuration yang sama. Pilihan anak difilter berdasarkan induk; saat induk diganti, tampilkan dampak lalu kosongkan pilihan turunan yang tidak sah setelah konfirmasi, bukan menyimpan ID lama yang tersembunyi. Popup tambah merek/model/seri/trim/konfigurasi tersedia sesuai izin; master pending approval tidak otomatis dapat dipakai. Saat unit dipilih, ringkasan menampilkan model/seri/trim, tahun, bahan bakar/mesin dan penggerak agar mekanik tidak hanya melihat nomor polisi. Unik kode dalam scope induk/pasar mencegah duplikasi; alias tidak mengganti validasi fitment. VIN/nomor rangka dan nomor mesin hanya ditampilkan kepada pihak berizin.


### 6.3 Kategori, status dan kebijakan pelanggan

**CUS-01 — Kategori pelanggan:** master kategori dengan kode, nama, status aktif dan kebijakan pembayaran berversi. Kategori **Umum** wajib tersedia dan menjadi default pelanggan baru/walk-in. Kategori lain, misalnya perusahaan/kontrak atau reseller, dapat ditambahkan sesuai bisnis; label kategori tidak otomatis memberi hak kredit atau membebaskan DP. Tanpa syarat pembayaran khusus yang disahkan, berlaku kebijakan dasar DP minimum 50%.

**CUS-02 — Status terpisah:** kategori pelanggan tidak disamakan dengan status operasional `aktif`, `nonaktif`, atau `hold transaksi`, tahap CRM prospek/pelanggan, maupun kelayakan kredit `belum disetujui`, `disetujui`, `ditangguhkan`. Alasan, pihak pengubah dan waktu berlaku disimpan. Pelanggan nonaktif/hold tidak dapat membuat komitmen baru atau merilis pekerjaan; penagihan saldo lama, pencatatan pembayaran, refund sah dan penyelesaian akuntansi tetap tersedia bagi pihak berizin.

**CUS-03 — Syarat pembayaran:** simpan persentase DP, dasar perhitungan, termin sisa, batas kredit, jatuh tempo, masa berlaku dan approval. Khusus kategori Umum, DP minimum 50% adalah aturan bisnis wajib dari owner, bukan nilai default yang dapat diturunkan oleh sales. Kategori lain hanya memakai syarat berbeda jika ada persetujuan owner/finance; kredit tetap diperiksa terhadap limit, umur piutang dan status aktifnya.

**CUS-04 — Snapshot dan pencegahan bypass:** kategori serta versi kebijakan pembayaran disalin ke penawaran/SO ketika disetujui. Mengubah master pelanggan atau mengganti kategori tidak otomatis menghapus kewajiban DP order berjalan. Amendemen memerlukan audit dan approval; selama order berkategori Umum, minimum 50% tetap tidak dapat diturunkan. Pelanggan yang kembali aktif wajib melewati pemeriksaan ulang pembayaran/kredit saat pekerjaan dirilis.

### 6.4 Detail identitas, kontak dan alamat pelanggan

**CUS-05 — Data profil:** form pelanggan harus menyediakan field terstruktur berikut, bukan hanya nama dan catatan bebas.

| Kelompok | Field | Aturan penggunaan |
| --- | --- | --- |
| Identitas | Kode pelanggan unik otomatis, jenis perorangan/badan usaha, nama lengkap/nama legal, nama panggilan/nama dagang | Kode, jenis dan nama wajib; nama panggilan tidak mengganti nama legal invoice |
| Kontak utama | Nomor telepon/HP, nomor WhatsApp bila berbeda, email, saluran komunikasi pilihan | Minimal satu telepon/HP aktif yang bisa dihubungi untuk job custom/kredit; email tidak wajib bila tidak tersedia |
| Perusahaan/PIC | Nama badan usaha, PIC utama, jabatan PIC, telepon/email PIC, PIC penagihan dan penerima kendaraan | Wajib PIC untuk pelanggan badan usaha; beberapa PIC dapat terhubung satu pelanggan |
| Alamat utama | Label, nama penerima, jalan/kompleks, nomor bangunan/unit, RT/RW bila berlaku, desa/kelurahan, kecamatan, kabupaten/kota, provinsi, kode pos, negara, patokan | Alamat lengkap wajib sebelum transaksi custom/kredit disetujui; bagian tidak berlaku boleh kosong dengan format negara yang sesuai, bukan diisi data palsu |

| Bisnis | Kategori, status, sales penanggung jawab, sumber pelanggan, syarat bayar, batas kredit, catatan layanan | Mengacu CUS-01–04; catatan tidak boleh menjadi pengganti field wajib |
| Hubungan transaksi | Kendaraan, quotation, order, job, DP, invoice, pembayaran, retur, garansi, tiket dan lampiran | Satu halaman profil menampilkan histori yang diizinkan dan saldo hingga dokumen sumber |

**CUS-06 — Validasi dan kualitas data:** nomor telepon disimpan sebagai string dengan kode negara yang dinormalisasi; format asli dapat ditampilkan untuk pengguna. Kode pos, NPWP dan nomor identitas juga bukan angka untuk operasi matematika. Kombinasi kontak/nama memberi peringatan calon duplikat, tetapi telepon bersama keluarga/perusahaan bukan alasan otomatis menggabungkan pelanggan. Penggabungan record hanya dengan izin khusus dan audit, menjaga referensi invoice/job lama. Customer import mengikuti validasi yang sama dengan form.

**CUS-07 — Tahap kelengkapan dan histori:** lead/prospek boleh disimpan belum lengkap dengan indikator data kurang; tidak boleh diluluskan menjadi order custom/kredit sebelum field wajib terpenuhi. Untuk retail anonim lunas yang diizinkan, gunakan profil walk-in eksplisit tanpa identitas fiktif; tetap berkategori Umum dan tidak boleh dipakai untuk kredit atau job kendaraan tanpa melengkapi identitas. Nama, kontak dan alamat penagihan/pengiriman disnapshot ke dokumen saat disetujui/posted; perubahan profil tidak mengganti invoice atau bukti kirim lama. Alamat memiliki kode wilayah sekaligus snapshot label agar pembaruan master wilayah tidak merusak histori.

**CUS-08 — Privasi dan komunikasi:** akses profil/lampiran mengikuti cabang, penugasan dan izin; data pajak/identitas/rekening refund memiliki hak sensitif terpisah. Persetujuan komunikasi pemasaran dicatat terpisah dari pesan transaksional. Perubahan rekening refund diverifikasi oleh finance; tidak dapat dipakai untuk mengalihkan pembayaran hanya dari pesan atau perubahan PIC tanpa verifikasi.

### 6.5 Purchase Request (PR)

**PR-01 — Pemicu dan sumber kebutuhan:** PR berasal dari kebutuhan warehouse (min/max, reorder point), BOM/usul material job, permintaan produksi, unit aset/maintenance, petty cash, marketing/umum, atau permintaan manual berizin. Sumber dan referensi (SO/job/WO/RFQ pelanggan) tersimpan; kebutuhan khusus pelanggan wajib dapat ditelusuri sampai SO.

**PR-02 — Field wajib:** nomor PR unik dari DocumentSequence per tipe; tanggal pengajuan; pemohon/departemen; cabang dan gudang tujuan; need-by date; prioritas; sumber/justifikasi; mata uang; daftar baris (SKU/deskripsi, qty dan satuan, estimasi harga bila ada, tanggal dibutuhkan per baris, catatan, lampiran spesifikasi); status; approver; jejak perubahan; penanda khusus job/evaluasi/stok.

**PR-03 — Approval berjenjang dan pemisahan tugas:** ambang nominal/disiplin memakai matriks approval ber-versi; pemohon tidak menyetujui PR-nya sendiri; kebutuhan darurat boleh memakai alur singkat dengan izin khusus, alasan, tenggat approval susulan, dan tidak boleh melewati pencatatan stok/biaya/jurnal. Penolakan wajib ber-alasan dan tersimpan.

**PR-04 — Status dan lifecycle:** `draft` → `diajukan` → `menunggu approval` (berjenjang bila ada) → `disetujui` → `ditolak` / `dibatalkan` → `dicover PO` (parsial atau penuh) → `selesai` / `ditutup`. Boleh ada `revisi` pra-approval; penyuntingan setelah approval memerlukan approval ulang atau mengembalikan status.

**PR-05 — Dedup dan kontrol anggaran:** baris yang sudah dicover PO tidak boleh dicover ulang lebih dari sisa qty; pembanding qty PR vs qty ter-PO vs qty diterima harus konsisten. PR diperiksa terhadap anggaran/komitmen bila modul anggaran aktif; PR di atas budget boleh diajukan tetapi perlu approval/justifikasi eksplisit. Draft PR, permintaan penawaran, dan jadwal tentatif boleh disiapkan **tanpa** menjadi otorisasi belanja atau pemicu release pekerjaan job DP (lihat SAL-09).

**PR-06 — Konsolidasi dan RFQ:** beberapa baris PR yang sama dapat dikonsolidasikan lintas job/cabang dengan jejak tetap per permintaan asal. Dari PR dapat diterbitkan permintaan penawaran ke beberapa vendor; perbandingan menampilkan harga neto, landed cost, lead time, minimum qty, kualitas/retur (lihat PUR-08). PR tidak mengharuskan PO; dasar pemilihan langsung-ke-PO dicatat.

**Contoh PR:** 3 unit winch 12.000 lb untuk job JOB-2026-0142, perlu 20 Okt 2026. PR disetujui, dicover parsial oleh 2 PO berbeda (2 unit + 1 unit); sisa qty PR menjadi nol dan PR berstatus `ditutup`, sementara masing-masing PO tetap melacak qty dan penerimaannya sendiri.

## 7. CRM, penawaran, dan kontrak pekerjaan

**SAL-01 — Lead sampai estimasi:** lead → survey/inspeksi → kebutuhan kendaraan → estimasi material, tenaga kerja, mesin, subkontrak, overhead → penawaran. Sumber lead dan alasan kalah/menang dicatat.

**SAL-02 — Penawaran berversi:** section per pekerjaan (misalnya bumper, winch, roll cage, suspensi); baris barang/jasa/paket; qty, harga, diskon, pajak, alternatif, masa berlaku, estimasi selesai, syarat bayar, garansi, pengecualian dan lampiran desain. Versi diterima dikunci; pelanggan tidak melihat biaya/margin internal. Penawaran yang dikirim dapat dibagikan lewat **tautan publik bertoken untuk e-sign** (`INT-04A`); versi yang di-supersede tidak dapat disetujui.

**SAL-03 — Kontrol margin:** tampilkan markup dan gross margin secara berbeda. Gross margin = (harga jual neto − biaya) / harga jual neto; markup = (harga jual neto − biaya) / biaya. Penawaran di bawah ambang membutuhkan approval dan alasan.

**SAL-04 — Konversi:** versi penawaran accepted — termasuk acceptance lewat tautan e-sign publik (`INT-04A`) — menghasilkan SO dan job/project beserta baseline budget secara atomik dan idempoten. Sebelum syarat DP SAL-09 terpenuhi, job berstatus menunggu DP dan WO belum boleh dirilis. Pembuatan dokumen/perencanaan tidak otomatis memberi izin mulai pekerjaan atau mengakui pendapatan.

**SAL-05 — Termin:** mendukung DP, progress billing, pelunasan, retensi dan kredit pelanggan. Invoice, pengakuan pendapatan, penerimaan uang, dan serah terima memiliki status terpisah. Pembayaran dapat dialokasikan ke beberapa invoice; kelebihan bayar tetap credit pelanggan atau direfund dengan approval.

**SAL-06 — Change order:** tambahan/perubahan pekerjaan mencatat revisi spesifikasi, harga, budget, lead time, persetujuan pelanggan dan internal. Baseline asli tetap tersedia; material dan jam tambahan terhubung ke change order.

**SAL-07 — Penjualan spare part langsung:** quotation/SO tidak wajib untuk transaksi counter yang diizinkan; invoice/penjualan, pembayaran dan pengeluaran stok tetap terhubung. Default rancangan untuk pelanggan Umum: penjualan langsung lunas sebelum barang diserahkan; pembayaran penuh sudah memenuhi minimum 50%, tidak perlu membuat pembayaran DP kedua. Pesanan retail yang tidak langsung diserahkan mengikuti gate DP SAL-09. Retur mengacu transaksi asal dan biaya asal, bukan harga beli terbaru.

**SAL-08 — Pembatalan:** hitung material terpakai, pekerjaan selesai, biaya pembatalan sah, DP yang dapat dikembalikan, dan sisa stok. Tidak menghapus histori job atau menyamakan seluruh DP dengan pendapatan.

### 7.1 DP wajib pelanggan umum

**SAL-13 — Surat jalan keluar dan bukti serah terima pelanggan:** pengeluaran barang jadi/spare part ke pelanggan memakai **surat jalan keluar (delivery order)** bernomor dari DocumentSequence, terpisah dari invoice dan dari pengakuan pendapatan. Field minimum: nomor surat jalan, tanggal kirim, referensi SO/job/garansi, pelanggan dan alamat kirim, daftar baris (SKU/deskripsi, qty dikirim, satuan, nomor lot/serial bila ada, kondisi kemasan), kendaraan/kurir dan plat, nama serta tanda tangan penerima, tanggal dan lokasi terima, lampiran foto dan dokumen. Surat jalan mendukung pengiriman parsial: **satu SO/job dapat dikirim bertahap** dan satu surat jalan dapat memuat beberapa baris. Barang yang keluar mengurangi qty tersedia di gudang dan berpindah ke posisi **barang dalam perjalanan / menunggu serah terima** yang terpisah dari pendapatan; pengakuan pendapatan dan pengakuan HPP mengikuti peristiwa yang disahkan (`FIN-02`, `FAB-12`), tidak otomatis saat barang keluar gudang.

Selisih qty dikirim vs qty diterima pelanggan dicatat per baris; barang yang ditolak/rusak saat serah terima diproses sebagai **retur masuk** kembali ke stok/karantina dengan alasan, bukan menghapus pengiriman. Bila pelanggan belum menerima, barang tidak dianggap terjual dan tidak boleh dipindahkan ke piutang. Surat jalan untuk pelanggan yang masih terkena gate DP (`SAL-09`) tetap memerlukan pemenuhan gate atau pengecualian kredit yang disetujui (`CUS-03`, `FIN-16`). Nomor surat jalan tidak dipakai ulang; surat jalan yang salah dibatalkan lewat reversal berreferensi, bukan diedit setelah diterima. Salinan serah terima menjadi bukti sah untuk klaim/garansi (`WAR-01`) dan wajib tersimpan meski dokumen ditutup.

**SAL-09 — Gate DP 50%:** pelanggan kategori **Umum wajib membayar minimum 50%** sebelum WO dirilis, fabrikasi/pemasangan dimulai, material dikeluarkan ke job, atau PO khusus job dikomitkan/dikirim ke vendor. Penawaran, inspeksi prapenawaran, job draft, PR draft dan jadwal tentatif boleh disiapkan, tetapi bukan otorisasi belanja/kerja. Pengadaan replenishment umum yang tidak khusus job tidak terkena gate ini; alokasi/issue berikutnya ke job tetap diperiksa. Gate diterapkan di backend untuk UI, API, impor dan transisi otomatis; role administrator bukan bypass. **Bedakan dua peristiwa berbeda:** gate DP 50% ini mengikat **mulai pekerjaan/komitmen pada order baru** (sebelum pekerjaan dimulai sama sekali), sedangkan **kekurangan DP akibat revisi harga di tengah pengerjaan** (`SAL-11`, `SAL-14`) tidak menghentikan pekerjaan lanjutan — ia hanya menahan perluasan lingkup dan belanja baru sampai selisih dibayar sah. Order yang sudah berjalan karena itu tidak "molor" kembali ke titik nol hanya karena harga naik.

Dasar perhitungan berikut merupakan **keputusan rancangan awal** yang dibuat eksplisit untuk review: 50% dari grand total pesanan yang telah disetujui pelanggan, sesudah diskon dan termasuk pajak serta biaya yang ditagihkan ke pelanggan. Pajak atas penerimaan DP tetap mengikuti FIN-04 dan tidak ditambahkan dua kali pada dasar tersebut.

```text
DP_minimum             = pembulatan_ke_atas_2_desimal(50% × grand_total_disetujui)
pembayaran_sah_order   = penerimaan terverifikasi dan posted yang dialokasikan ke order
                        − refund/reversal pembayaran terkait
kekurangan_DP          = max(0, DP_minimum − pembayaran_sah_order)
boleh_rilis_pekerjaan  = kekurangan_DP = 0 dan seluruh gate lain terpenuhi
```

**SAL-10 — Verifikasi pembayaran:** bukti transfer terunggah, janji bayar, invoice DP diterbitkan, transfer pending/gagal dan credit limit bukan pembayaran sah. Penerimaan tunai/bank harus diverifikasi petugas berwenang dan diposting; DP boleh dicicil hingga jumlah minimum terpenuhi. Satu penerimaan tidak boleh dialokasikan melebihi nominalnya atau dihitung penuh pada dua order. Saat DP dialokasikan ke invoice, histori penerimaan order tetap dihitung satu kali; perpindahan dari akun uang muka ke piutang tidak membuat gate kembali gagal. Dana tetap mengikuti FIN-02: penerimaan DP bukan otomatis pendapatan.

**SAL-11 — Revisi, refund dan pemeriksaan ulang:** hitung kembali syarat DP saat nilai pesanan berubah melalui change order approved, pembayaran direverse/direfund atau alokasinya dipindah. Jika kurang, tampilkan payment hold dan blokir **komitmen pembelian khusus job, komitmen baru dan issue material baru** sampai top-up sah. **Pekerjaan lanjutan tidak dihentikan** oleh hold ini: unit yang sudah dibongkar dan sedang dikerjakan tetap diselesaikan dengan pemakaian material/jam yang sudah berjalan, karena menghentikan pekerjaan justru menambah biaya dan kerusakan; yang ditahan adalah perluasan lingkup dan belanja baru. Pekerjaan lanjutan atas **selisih harga yang belum disetujui/dibayar** tidak boleh dipaksakan melebihi apa yang sudah dikerjakan atas persetujuan yang ada. Transaksi posted dan pekerjaan yang sudah terjadi tidak dihapus; pemakaian aktual yang telanjur terjadi serta tindakan pengamanan tetap dicatat untuk audit, bukan disembunyikan karena gate. Penurunan nilai kontrak dapat mengurangi kebutuhan DP tetapi tidak otomatis merefund uang; refund memakai alur approval tersendiri. Pemeriksaan gate dan perubahan pembayaran/alokasi diserialisasi dalam transaksi agar release bersamaan tidak lolos dua kali atau saling menimpa.

**SAL-12 — Contoh dan tampilan:** pesanan Rp20.000.000 membutuhkan DP Rp10.000.000. Pembayaran sah Rp6.000.000 → masih menunggu Rp4.000.000; tambahan Rp4.000.000 → boleh dirilis jika gate lain lolos. Jika nilai approved menjadi Rp24.000.000, minimum menjadi Rp12.000.000 dan perlu tambahan Rp2.000.000. Tampilkan kategori pelanggan, versi syarat bayar, total dasar, persentase, nominal minimum, penerimaan sah, refund/reversal, kekurangan, status hold dan sisa tagihan pada penawaran, SO, job dan dashboard finance. Jadwal pelunasan sisa harus dinyatakan dalam penawaran; kewajiban DP 50% tidak berarti otomatis menyetujui kredit untuk sisanya.

**SAL-14 — Pekerjaan custom: harga fleksibel sampai serah terima:** karena lingkup pekerjaan custom (misalnya fabrikasi roll cage, bumper, suspensi atau kelistrikan) **dapat berubah di tengah pengerjaan**, harga pada SO/invoice **belum bersifat final selama unit belum diserahkan dan diterima pelanggan**. Perubahan harga selama pengerjaan dicatat sebagai revisi resmi bernomor (`change order`, `SAL-06`), bukan penyuntingan senyap atas harga yang sudah dikirim ke pelanggan. Setiap revisi memuat: alasan (material tambahan, kondisi temuan saat bongkar, permintaan pelanggan, penyesuaian harga material), daftar baris yang berubah, harga sebelum dan sesudah, selisih, siapa yang mengusulkan, approval internal, **persetujuan pelanggan** (boleh lewat tautan e-sign `INT-04A`), dan dasar waktu.

Arus dokumen yang benar: **penawaran diterima → SO aktif → harga berubah berulang kali → pelanggan menyetujui revisi terakhir → invoice final diterbitkan saat/setelah serah terima → pembayaran diselesaikan.** Selama pekerjaan berjalan, dokumen yang beredar adalah **invoice sementara/DP/progress billing** yang boleh direvisi mengikuti revisi harga; angka itu **bukan** harga final dan tidak boleh dipakai sebagai dasar pengakuan pendapatan. Kenaikan harga selalu membawa serta konsekuensi gate DP (`SAL-09`, `SAL-11`): bila grand total naik, minimum DP ikut naik dan sistem menampilkan hold sampai selisihnya dibayar sah; **namun hold itu tidak menghentikan pekerjaan lanjutan** pada unit yang sudah dibongkar — hanya menahan perluasan lingkup dan belanja baru. Bila grand total turun, kebutuhan DP ikut turun tanpa otomatis merefund uang yang sudah masuk.

Bila pelanggan **menolak** selisih harga pada revisi, pekerjaan atas selisih itu tidak boleh dipaksakan: pilihannya menghentikan pekerjaan tambahan, mengembalikan spesifikasi ke baseline semula, atau menempuh pembatalan (`SAL-08`). Pekerjaan yang telanjur dikerjakan atas permintaan pelanggan maupun perubahan yang disetujui tetap harus dapat dipertanggungjawabkan meski pelanggan kemudian berubah pikiran; material dan jam yang sudah terjadi tidak dihapus. Setelah serah terima diterima, harga terkunci dan perubahan sesudahnya hanya bisa lewat mekanisme baru (garansi `WAR-01`, retur `SAL-05`, atau pekerjaan baru), bukan lewat revisi diam-diam atas invoice yang sudah final.

## 8. Pembelian marketplace dan pengadaan

### 8.1 Alur dan dokumen

**PUR-01:** kebutuhan dari BOM/job/reorder/manual → PR → penawaran pemasok/perbandingan → approval → PO → pembayaran muka bila perlu → pengiriman → GRN/QC → matching tagihan → pelunasan → penutupan.

Pembelian mendesak boleh memakai alur singkat dengan izin khusus, bukti dan approval susulan yang memiliki tenggat; tidak boleh melewati pencatatan stok, biaya, dan jurnal.

### 8.2 Dokumen Purchase Order dan GRN

**PUR-02 — Struktur marketplace:** satu checkout dapat mencakup banyak toko, PO, pengiriman, penerimaan dan tagihan. Entitas checkout tidak dianggap satu pemasok. Simpan platform, akun pembeli, nomor checkout/order/toko, nomor resi, link, timestamp, screenshot/invoice, metode bayar, dan pihak pembayar.

**PUR-03 — Komponen nominal:** harga gross per baris, diskon baris, voucher order tambahan, subsidi ongkir, ongkir dibayar pembeli, asuransi, packing, biaya admin/platform, pajak recoverable/nonrecoverable, serta cashback dengan status belum berhak/diakui/diterima. Tampilkan bridge dari harga listing ke biaya perolehan dan kas dibayar.

**PUR-04 — Pemisahan pembayaran:** rekening perusahaan, wallet marketplace, kartu kredit perusahaan, uang pribadi karyawan/owner, dan escrow memiliki akun perantara masing-masing. Pembelian memakai uang pribadi membentuk kewajiban reimbursement, bukan pengeluaran bank perusahaan palsu. Kartu kredit membentuk utang kartu hingga tagihan dibayar.

**PUR-05 — Pembayaran awal/escrow:** dana keluar sebelum barang diterima tercatat sebagai uang muka pemasok/dana escrow, bukan langsung beban atau persediaan. Perpindahan ke wallet dan pemakaian wallet merupakan peristiwa berbeda agar kas tidak dihitung dua kali.

**PUR-06 — Penerimaan:** qty baik, rusak, kurang, salah barang, karantina, dan ditolak dipisahkan. Penerimaan parsial, split shipment, beberapa gudang, foto dan serial didukung. Over-receipt ditolak kecuali perubahan PO disetujui lebih dulu. Status marketplace “selesai” tidak otomatis berarti barang sudah diterima internal.

**PUR-07 — Three-way match:** PO ↔ GR ↔ invoice vendor mencocokkan qty, harga, diskon, pajak dan biaya. Selisih toleransi tetap masuk akun/penyesuaian yang terlihat; di atas toleransi memblokir posting/pembayaran sesuai kebijakan. Invoice sebelum GR dicatat sebagai tagihan belum matched, tidak membuat qty stok fiktif.

**PUR-08 — Pembanding pemasok:** tampilkan harga neto dan landed cost per satuan dasar, tanggal, toko/platform, lead time, kualitas/retur, minimum qty dan total biaya pemenuhan. Jangan memberi rekomendasi berdasarkan harga listing saja.

### 8.3 Diskon, cashback, retur, dan penutupan

**PUR-09 — Diskon tepat sekali:** diskon baris mengurangi baris itu sendiri. Voucher order hanya alokasi tambahan untuk item eligible; field total diskon merupakan agregat, tidak dikurangkan lagi. Subsidi ongkir mengurangi ongkir, bukan sekaligus mengurangi harga barang. Struktur ini sengaja memperjelas ambiguitas data lama.

**PUR-10 — Cashback:** cashback bersyarat/poin yang belum menjadi hak tidak mengurangi HPP awal. Saat menjadi hak terukur, klasifikasikan menurut substansi yang disahkan finance: rebate pembelian → adjustment biaya lot terkait; insentif non-pembelian → akun pendapatan lain. Saldo wallet, kas diterima, dan hak cashback tidak boleh dicatat sebagai tiga pendapatan terpisah. Pembatalan/expired mengikuti kebijakan dan audit.

**PUR-11 — Retur/refund:** retur barang, credit note dan penerimaan refund merupakan peristiwa terpisah; dukung refund sebagian, tanpa retur, ongkir tidak dikembalikan, barang pengganti, refund ke wallet dan klaim tertunda. Pengembalian ke vendor memakai lot/biaya asli; selisih nominal refund terhadap biaya barang dan biaya tidak recoverable dicatat eksplisit.

**PUR-12 — Tutup PO:** alasan short-close, qty batal, sisa uang muka/refund, biaya belum dialokasikan dan selisih clearing wajib diselesaikan atau direklasifikasi ke akun klaim/accrual yang beralasan. Menutup qty pesanan tidak otomatis menghapus ongkir yang benar-benar telah dibayar. Estimasi biaya yang tidak terjadi dibatalkan, bukan dipaksakan ke HPP.

### 8.4 Utang vendor, pembayaran, dan termin

**PUR-13 — Purchase Order (PO):** PO diterbitkan dari PR yang disetujui atau jalur langsung berizin. Field minimum: nomor PO; vendor/stores dan penerbit invoice; tanggal PO; tanggal kirim diharapkan; syarat bayar vendor (lihat FIN-15); mata uang dan kurs bila berbeda; syarat kirim/Incoterm lokal; faktur pajak; alamat kirim/gudang; daftar baris (SKU, qty dipesan, harga gross, diskon baris, pajak, uoM, tanggal butuh, special order flag, referensi PR/baris); ongkir/biaya lain; total; lampiran (penawaran, gambar); perubahan versi/revisi PO dengan approval. Status: `draft` → `disetujui` → `dikirim/dikonfirmasi vendor` → `sebagian diterima` → `diterima penuh` → `ditutup`/`dibatalkan`/`short-close` (PUR-12).

**PUR-14 — Komitmen dan kontrol perubahan:** PO disetujui adalah komitmen; over-receipt (PUR-06) dan penerimaan di atas qty PO ditolak kecuali perubahan PO lebih dulu disetujui. Perubahan qty/harga/bank/term setelah baris diterima tidak menimpa histori; revisi memakai versi. Membatalkan PO yang sudah menerima pembayaran muka wajib menuntaskan uang muka (refund/realokasi), bukan menghapusnya. PO khusus job tetap terikat gate DP (SAL-09).

**PUR-15 — Penerimaan barang / GRN (Goods Receipt Note):** GRN dibuat per pengiriman dan per gudang; boleh parsial dan split shipment. Field: nomor GRN; tanggal terima aktual; referensi PO/baris dan vendor; SKU/deskripsi; qty harus/dipesan/terima; satuan; harga per uoM; nomor lot/serial; kondisi per baris (`baik`, `rusak/karantina`, `kurang`, `salah barang`, `ditolak`); nama penerima/gudang; QC checklist; dokumen surat jalan/invoice/plat kendaraan kurir; lampiran foto; tanggal & user. GRN membuat **layer biaya per penerimaan** (lihat bab 9) dan menjadi dasar GRNI bila invoice vendor belum diterima (FIN-16, REP-11). Status: `draft` → `posted/verified` → `sebagian ditagih` → `ditagih penuh` → `ditutup`, plus `dibatalkan` via reversal (draft-only edit).

**PUR-15A — Surat jalan masuk vendor (delivery note pemasok):** surat jalan vendor dicatat sebagai dokumen tersendiri yang merujuk PO, bukan sekadar lampiran di dalam GRN. Field minimum: nomor surat jalan vendor, tanggal surat jalan, tanggal kirim aktual, vendor/asal, nomor PO, daftar baris (SKU/deskripsi, qty menurut surat jalan, satuan, nomor lot/serial bila ada), kendaraan/plat/pengangkut, nama dan tanda tangan pengantar, penerima di gudang, dan lampiran dokumen. Sistem membandingkan qty menurut surat jalan dengan qty diterima pada GRN; **selisih dicatat sebagai item outstanding vendor** (kurang kirim, lebih kirim, salah barang) yang terbuka sampai diselesaikan, sehingga tidak hilang dari tagihan maupun klaim (`PUR-11`, `PUR-16`). Satu surat jalan dapat mencakup beberapa PO/baris dan satu PO dapat diterima lewat beberapa surat jalan. Surat jalan tanpa PO hanya boleh diterima lewat dokumen penerimaan khusus ber-approval. Surat jalan vendor belum tentu menjadi dasar utang: **utang tetap diakui dari GRN** (`FIN-13`), surat jalan hanya bukti kirim. Nomor surat jalan vendor unik dalam scope vendor agar tidak dipakai dua kali untuk klaim ganda.

**PUR-16 — Aturan qty dan QC GRN:** qty baik menambah stok; qty rusak/karantina masuk karantina, tidak menambah stok tersedia untuk konsumsi normal; qty kurang/salah barang tetap tercatat sebagai outstanding vendor sehingga tidak hilang dari tagihan. Over-receipt ditolak kecuali perubahan PO disetujui. Barang tanpa PO (donasi/garansi/koreksi) memakai dokumen penerimaan khusus ber-approval. **Status marketplace "selesai" tidak otomatis berarti barang diterima internal** (PUR-06). GR adalah satu-satunya jalur yang boleh membuat qty stok dan layer; jurnal manual tidak boleh menambah qty.

**PUR-17 — Penerimaan jasa/subkontrak:** jasa lurus dengan GRN jasa (qty/harga/progress) tanpa layer stok; subkontrak memakai penerimaan material di vendor dan return, dengan dokumen penerimaan internal terpisah.

**PUR-18 — Siklus utang vendor:** daftar utang per vendor dengan umur dan jatuh tempo; pembayaran sebagian/penuh; satu pembayaran boleh mengalokasi beberapa tagihan (many-to-many) dan satu tagihan boleh dibayar bertahap; uang muka vendor diperhitungkan lebih dulu atau direfund; payment advice/remittance; pembayaran via bank transfer (diusulkan/di-approve, bukan asumsi otomatis ke bank), wallet marketplace, kartu kredit perusahaan (membentuk utang kartu sampai tagihan dibayar), atau cash. Field pembayaran: nomor, tanggal, metode, rekening asal, referensi bank/bukti, jumlah, alokasi, penerima, approval dua pihak untuk nominal sensitif, dan status verifikasi/posting.

**PUR-19 — Batal, retur, dan penyelesaian:** pembayaran salah/duplikat dibatalkan via reversal berreferensi dokumen asal; pembatalan nomor bukti dianggap tidak ada; kelebihan bayar menjadi uang muka vendor atau refund sesuai kesepakatan. Retur vendor memakai lot/biaya asal (PUR-11); setelah retur, utang/GRNI/kredit nota harus konsisten. Statement of account vendor direkonsiliasi berkala, selisih terbuka sebagai item penyelesaian, bukan dihapus.

**PUR-20 — Vendor tanpa termin khusus dan manajemen vendor:** termin default vendor baru bila tidak disahkan adalah COD (bayar saat terima) atau CBD sesuai kesepakatan; sistem tidak boleh mengasumsikan kredit 30 hari tanpa perjanjian. Rating, lead time, riwayat retur dan kualitas vendor dipakai sebagai dasar pemilihan dan evaluasi (PUR-08).

**MD-08 — Syarat bayar (payment terms) master:** termin disimpan sebagai master ber-versi memuat kode, label, tipe (`COD`, `CBD`, `net`, `installment`), basis hari, jumlah termin, diskon pelunasan cepat (contoh 2/10 Net 30) bila disahkan, dan status aktif. Term disnapshot ke PO dan tagihan; mengubah master tidak mengubah jatuh tempo dokumen posted. Term default vendor disimpan di master vendor (MD-04) dan boleh ditimpa per PO dengan approval.

**MD-08A — Master metode pembayaran:** metode pembayaran disimpan terpisah dari termin karena menjawab *bagaimana* dibayar, bukan *kapan*. Field minimum: kode/nama, jenis (`transfer bank`, `virtual account`, `QRIS`, `tunai`, `giro/cek`, `kartu kredit perusahaan`, `wallet`, `escrow/dana pihak ketiga`), mata uang, rekening/akun lawan bertanggal, biaya admin atau biaya platform bila ada, batas nominal minimum/maksimum, apakah memerlukan bukti/referensi bank, dan status aktif. Metode disnapshot ke PO, tagihan vendor dan invoice pelanggan sehingga mengubah master tidak mengubah dokumen posted. Metode tidak menggantikan termin maupun gate DP: pembayaran yang masih butuh verifikasi (transfer pending/gagal, janji bayar) belum menjadi pembayaran sah (`SAL-10`, `FIN-15`). Biaya admin diklasifikasikan sebagai biaya terpisah, bukan penambah pokok utang/piutang tanpa dasar. Metode yang membentuk instrumen (kartu kredit perusahaan, giro) memiliki perlakuan utang/instrumen tersendiri (`PUR-18`) dan tanggal jatuh tempo instrumennya. Metode khusus yang dihapus tidak menghapus histori transaksi yang memakainya.

**MD-08B — Master harga pekerjaan custom (price list fleksibel):** harga pekerjaan custom tidak selamanya bisa ditetapkan penuh di depan, jadi disimpan sebagai **master harga ber-versi** yang menjadi sumber tunggal saat menyusun penawaran, revisi, dan invoice custom. Isi minimum per item: kode/nama pekerjaan atau jasa (misalnya pasang roll cage, ganti suspensi, perbaikan kelistrikan), kelompok (jasa/fabrikasi/part/subkontrak), satuan (unit, jam, meter, set), **harga dasar**, rentang/multiplier bila berlaku, harga minimum, biaya material terpisah, status aktif, tanggal berlaku, dan **versi**. Master diperlakukan berbeda dari harga jual produk standar (`MD-06`) karena sifatnya fleksibel.

Master ini tidak berarti semua custom memakai harga tetap: pekerjaan yang tetap boleh dikustom, tetapi **nilai yang sudah dipakai pada dokumen disnapshot** sehingga mengubah master tidak menimpa penawaran/invoice yang sudah terbit. Setiap item harus bisa melewati jalur **revisi resmi** (`SAL-14`) dengan jejak versi yang sama seperti master lain; item yang perlu harga di luar master (misalnya material langka) tetap boleh, tetapi **wajib melalui approval** berjenjang (`SAL-03` untuk kontrol margin) dan alasannya tercatat. Master ini juga menjadi dasar tampilan harga di aplikasi internal supaya mekanik/sales tidak mengarang angka; perubahan master hanya oleh peran berizin dan tercatat audited.

**MD-09 — Katalog dan aturan termin:**

| Kode | Arti | Rumus jatuh tempo | Catatan |
| --- | --- | --- | --- |
| COD | Bayar saat serah terima | tanggal serah terima | Tidak membentuk utang; kas/bank langsung |
| CBD | Bayar saat dokumen/tagihan diterima | tanggal terima tagihan | Dasar disahkan finance |
| Net 7 / 14 / 30 / 45 / 60 / 90 | Bayar dalam N hari | `tanggal_basis + N hari` | Basis default **tanggal invoice**; alternatif tanggal GRN/dokumen disahkan eksplisit |
| 2/10 Net 30 | Diskon bila bayar ≤ 10 hari | jatuh tempo basis + 30 hari | Diskon pelunasan diperlakukan sebagai pengurang biaya barang/akun disetujui, bukan penghapusan utang sepihak |
| Installment | Bayar bertahap | tanggal per termin | Dipakai bila vendor memberi termin parsial |

**Contoh utang vendor dengan termin:** Invoice vendor Rp5.000.000 tanggal **1 Okt 2026**, termin **Net 30** → jatuh tempo **31 Okt 2026**. Bila barang sudah diterima GRN 25 Sep 2026 dengan basis tanggal GRN yang disetujui, jatuh tempo bergeser menjadi **25 Okt 2026**; pilihan basis dicatat sebagai kebijakan, bukan otomatis. Pembayaran parsial Rp2.000.000 tanggal 25 Okt 2026 menyisakan utang Rp3.000.000 dengan umur 30 hari pada cutoff 31 Okt 2026.

### 8.5 Piutang pelanggan dan penagihan

**Contoh piutang:** Invoice INV-2026-0417 Rp20.000.000 tanggal 2 Okt 2026, termin **Net 30** → jatuh tempo **1 Nov 2026**. DP sah Rp10.000.000 dialokasikan sehingga sisa piutang Rp10.000.000. Pada cutoff 31 Okt 2026 belum jatuh tempo (0 hingga 30 hari); tunggakan dihitung bila pembayaran belum diterima per 1 Nov 2026.

## 9. HPP, FIFO, dan landed cost

### 9.1 Sumber kebenaran

**CST-01:** saldo qty berasal dari mutasi stok posted per SKU/lokasi/kepemilikan; nilai persediaan berasal dari layer dan ledger penyesuaian biaya. Cache qty bukan sumber costing. Setiap konsumsi menyimpan layer sumber, qty, nilai, tujuan job/produk, dan referensi jurnal.

**CST-02:** FIFO memakai urutan posting penerimaan yang tidak berubah dan tie-breaker ID; tanggal dokumen/backdate tidak menyisipkan layer diam-diam ke konsumsi lama. Transfer mempertahankan umur asal, identitas biaya, dan jejak lot. Serial fisik yang dipilih harus cocok dengan layer sumber; pengecualian pemilihan lot dicatat dengan alasan, bukan konsumsi lot fiktif.

**CST-03:** qty negatif, konsumsi ganda, layer sisa negatif, dan cache cukup tetapi layer kurang harus ditolak. Lock baris dan transaksi atomik diperlukan pada konsumsi bersamaan. Barang gratis boleh memiliki biaya barang nol jika eksplisit dan disetujui; tidak boleh membuat layer nol sebagai fallback error.

### 9.2 Rumus target

Untuk baris penerimaan i, semua nilai tidak termasuk pajak yang dapat dikreditkan:

```text
nilai_gross_i         = qty_diterima_i × harga_gross_per_UoM_transaksi_i
nilai_setelah_baris_i = nilai_gross_i − diskon_baris_untuk_qty_diterima_i
nilai_neto_i          = nilai_setelah_baris_i − alokasi_voucher_tambahan_i
biaya_perolehan_i    = nilai_neto_i + alokasi_biaya_kapitalisasi_i
                       + pajak_nonrecoverable_i
qty_dasar_i          = qty_diterima_i × faktor_ke_satuan_dasar_i
unit_cost_i          = biaya_perolehan_i / qty_dasar_i
```

**CST-04:** biaya kapitalisasi hanya biaya yang secara langsung membawa barang ke lokasi/kondisi siap digunakan: ongkir, asuransi pengiriman, handling, bea masuk, dan komponen lain sesuai kebijakan. Biaya pembiayaan, penalti keterlambatan, dan biaya abnormal tidak otomatis masuk HPP. Pajak masukan yang recoverable dicatat terpisah; status PKP dan bukti pajak menentukan perlakuan, bukan nama field saja.

**CST-05 — Allocation pool:** setiap komponen biaya/voucher memiliki ID sumber, scope (baris/shipment/GR/order), nilai estimasi, nilai aktual, currency/kurs, basis alokasi, penerima alokasi dan saldo belum dialokasikan. Total alokasi seluruh GR tidak boleh melebihi pool yang tersedia. Jangan menyalin total ongkir PO ke setiap GR.

**CST-06 — Basis:** default ongkir bersama dialokasikan proporsional nilai neto barang eligible. Biaya yang jelas untuk satu barang dialokasikan langsung. Berat/volume/qty dapat dipilih untuk ongkir material besar dengan data dan alasan terdokumentasi. Voucher mengikuti eligibility dan batas promonya. Jika seluruh nilai eligible nol, pilih basis qty/berat secara eksplisit; jangan membagi nol atau membuang biaya.

**CST-07 — Estimasi versus aktual:** status biaya `estimated`, `actual`, atau `pending` terpisah dari nominal. Actual 0 berarti ongkir gratis yang sudah diketahui, bukan “pakai estimasi PO”. Posting provisional boleh jika disetujui; laporan memberi tanda belum final. Penetapan aktual kemudian hanya membukukan selisih terhadap estimasi yang sudah diakui.

**CST-08 — Penerimaan parsial:** biaya khusus GR seluruhnya dialokasikan ke GR itu; pool bersama dialokasikan menurut basis yang disepakati dan dicatat kumulatif. Saat PO short-close, biaya bersama aktual yang masih terkait barang diterima dialokasikan ulang lewat adjustment. Biaya abnormal atau klaim refund dipisahkan; tidak semua saldo otomatis dibebankan ke stok.

**CST-09 — Presisi:** nilai dokumen/jurnal IDR disimpan desimal dua tempat; qty, faktor UoM, unit cost dan perhitungan antara memiliki presisi lebih tinggi yang ditetapkan saat desain data. Tidak menggunakan binary float untuk uang. Nilai total layer otoritatif dipertahankan; konsumsi terakhir menyerap residual pembulatan. Selisih alokasi ke baris berbobot terbesar, tie-breaker ID. Total selalu cocok sampai Rp0,01; pembulatan rupiah tampilan tidak mengubah ledger.

### 9.3 Koreksi biaya setelah posting

**CST-10:** dokumen posted tidak diedit/hapus langsung. Landed-cost adjustment menyimpan biaya lama, biaya baru, selisih, bukti, approval, tanggal efektif dan alokasi ke keturunan layer. Histori posting awal tetap tersedia.

Distribusi selisih mengikuti lokasi biaya saat adjustment:

- Masih menjadi bahan baku: nilai persediaan bahan baku.
- Sudah ditransfer: persediaan di gudang tujuan, bukan gudang asal.
- Sudah dipakai job yang belum diakui sebagai HPP: WIP job.
- Sudah menjadi produk jadi belum terjual: persediaan barang jadi melalui genealogi produksi.
- Sudah terjual/diserahterimakan: HPP/akun koreksi biaya dengan dimensi job asal.
- Sudah diretur atau di-scrap: akun klaim/selisih/kerugian yang sesuai, bukan stok yang sudah tidak ada.

Periode terkunci tidak ditulis ulang. Adjustment masuk periode terbuka yang disetujui, tetap menautkan transaksi/job asal. Laporan membedakan hasil pada saat closing dengan lifetime job cost yang sudah diperbarui. Pengurangan biaya tidak boleh membuat nilai stok negatif; kelebihan refund yang bukan pengurang perolehan diklasifikasi terpisah dengan approval.

**CST-11 — Clearing:** barang diterima belum ditagih dan biaya angkut belum ditagih mempunyai rincian accrual terpisah. Invoice barang hanya membersihkan accrual barang; invoice kurir membersihkan accrual ongkir. Matching wajib per sumber biaya. Sisa clearing terlihat menurut umur dan sebab, tidak dihapus lewat jurnal penyeimbang tanpa referensi.

### 9.4 Contoh angka wajib

**Contoh A — SKU sama, toko/harga berbeda; tanpa pajak.**

| Komponen | Lot toko X | Lot toko Y |
| --- | ---: | ---: |
| Qty | 10 pcs | 10 pcs |
| Harga gross/unit | Rp100.000 | Rp95.000 |
| Nilai gross | Rp1.000.000 | Rp950.000 |
| Diskon baris total | Rp100.000 | Rp0 |
| Voucher tambahan | Rp0 | Rp50.000 |
| Ongkir aktual yang dikapitalisasi | Rp50.000 | Rp120.000 |
| Biaya perolehan total | Rp950.000 | Rp1.020.000 |
| Biaya per unit | Rp95.000 | Rp102.000 |

Toko Y memiliki harga listing lebih murah tetapi biaya perolehan lebih mahal. Bila lot X lebih dahulu dan job mengambil 12 pcs: HPP material = 10 × Rp95.000 + 2 × Rp102.000 = **Rp1.154.000**. Sisa lot Y = 8 pcs bernilai **Rp816.000**. Tidak menggunakan harga terakhir Rp95.000 untuk seluruh pemakaian.

**Contoh B — Satu ongkir untuk dua barang.** Nilai neto A Rp900.000 dan B Rp300.000; ongkir Rp120.000. Alokasi A Rp90.000 dan B Rp30.000. Total persediaan Rp1.320.000. Jika invoice barang Rp1.200.000 dan invoice kurir Rp120.000, keduanya membersihkan accrual masing-masing hingga nol.

**Contoh C — Parsial dan short-close.** PO 10 pcs, ongkir aktual bersama Rp100.000; alokasi awal berdasar qty homogen yang direncanakan. Terima 4 pcs → Rp40.000 teralokasi; terima 6 pcs → Rp60.000. Jika sisa 6 dibatalkan dan seluruh ongkir memang untuk 4 pcs tadi, Rp60.000 tambahan harus dialokasikan lewat adjustment. Jika 2 pcs sudah digunakan ke WIP dan 2 masih di gudang, masing-masing menerima tambahan Rp30.000. Bila Rp60.000 justru dapat direfund, catat klaim refund, bukan tambahan HPP.

**Contoh D — Biaya terlambat.** Lot 10 pcs menerima tambahan ongkir Rp50.000 setelah 6 pcs sudah menjadi HPP job selesai dan 4 masih di gudang: Dr persediaan Rp20.000, Dr HPP job Rp30.000, Cr accrual/utang Rp50.000. Jika 6 pcs masih dalam pengerjaan, debit Rp30.000 ke WIP, bukan HPP.

## 10. Gudang, material fabrikasi, dan stok

**INV-01:** multi-gudang, rak/bin, stock card, barcode/QR, lot/serial, expiry bila relevan, reservasi untuk job/SO, qty available = on hand usable − reserved. Reserved tidak memindahkan nilai akuntansi.

**INV-02:** transfer memakai alur kirim → in transit → terima; dukung parsial, kerusakan dan selisih dengan investigasi. Nilai total perusahaan tidak berubah karena transfer internal.

**INV-03:** stock opname/cycle count menggunakan snapshot/cutoff dan aturan gerakan selama hitung. Selisih memerlukan recount/approval; posting mencatat akun gain/loss dan dimensi gudang. Tidak mengubah master qty secara manual.

**INV-04:** material issue terhubung job/production order, tahap, komponen BOM, qty diminta/keluar/kembali, konsumsi layer, petugas dan waktu. Material substitusi membutuhkan persetujuan engineering jika memengaruhi spesifikasi/keamanan.

**INV-05:** sisa potongan pipa/plat (remnant) menyimpan grade, dimensi, qty/berat, lokasi dan biaya bawaan. Split material mempertahankan total qty ekuivalen dan nilai: bahan terpakai + remnant reusable + scrap/loss. Remnant bernilai tidak otomatis ditulis nol.

**INV-06:** scrap normal masuk biaya hasil produksi sesuai kebijakan; scrap abnormal dipisahkan ke kerugian. Penjualan scrap mempunyai qty, bukti timbang, penerimaan kas dan perlakuan pendapatan/pengurang biaya yang disetujui. Jangan menghitung nilai scrap dua kali sebagai remnant dan pendapatan.

**INV-07:** barang rusak/karantina tidak tersedia untuk reservasi/pemakaian. Barang diterima secara kepemilikan tetapi karantina dapat bernilai persediaan dengan status tidak usable; barang ditolak tanpa perpindahan kepemilikan tidak dibukukan sebagai milik bengkel.

**INV-08 — Hierarki lokasi gudang (zona, row, rak, level, posisi):** lokasi penyimpanan tidak berhenti di "rak/bin", karena gudang fabrikasi menampung barang dengan bentuk sangat berbeda — plat 4×8 kaki, pipa panjang, remnant potongan, komponen kecil, dan alat ukur. Karena itu lokasi disimpan sebagai **hierarki berjenjang**: `gudang → zona → row/baris → rak → level/tingkat → bin/posisi`. Kedalaman tidak wajib seragam: gudang yang hanya memakai rak sederhana boleh berhenti di dua tingkat, dan lokasi tetap dapat dicatat sebagai **kode lokasi bertingkat** (misalnya `GD-A-R03-L2-B05`) sehingga penelusuran tidak bergantung jumlah tingkat yang dipakai. Setiap tingkat menyimpan kode, nama, induk yang sah, status aktif, dan urutan tampil; kode unik dalam scope induknya.

Setiap lokasi menyimpan **tipe**: `bin` (barang kecil/komponen), `rak panjang` (pipa/profil/plat), `lantai/floor` (barang besar atau berat), `area remnant` (sisa potongan `INV-05`), `karantina` (`INV-07`), dan `staging/in-transit`. Tipe membatasi barang apa yang boleh ditempatkan, sehingga **kapasitas** (qty maksimum, berat maksimum, dan dimensi/panjang maksimum) dapat diperiksa: sistem menolak menaruh plat berukuran besar di bin kecil atau pipa panjang di rak pendek. **Aturan lokasi per item** (misalnya plat hanya di `rak panjang`/`lantai`, pipa hanya di `rak panjang`, remnant hanya di `area remnant`) menjadi default putaway; item yang memerlukan pengecualian harus disetujui dan dicatat alasannya.

**Putaway dan picking dibimbing sistem:** saat penerimaan (`PUR-06`) atau penerimaan transfer (`INV-02`) sistem mengusulkan lokasi tujuan sesuai tipe/kapasitas/aturan item, dan saat material issue (`INV-04`) sistem menunjuk lokasi pengambilan beserta urutannya agar petugas tidak menebak. Item yang wajib berposisi **tidak boleh** dicatat tanpa lokasi; bila lokasinya belum ditentukan, barang masuk sebagai `unlocated` pada gudangnya dan **wajib** dirapikan dalam tenggat yang disahkan, bukan dibiarkan permanen. Satu qty item dapat berada di beberapa lokasi (split lokasi) dan satu lokasi dapat memuat beberapa item/lot/serial; total qty per item tetap harus sama dengan total per lokasi. Pemindahan antar lokasi **di dalam gudang yang sama** tidak mengubah nilai persediaan (sama seperti transfer internal `INV-02`), tetapi tetap mencatat pergerakan berpetugas dan bertanggal untuk audit. Lokasi yang masih menyimpan stok tidak boleh dinonaktifkan atau dihapus; histori lokasi tidak menghapus pergerakan lama.

**Keputusan rancangan (`INV-08`):** mengingat bengkel fabrikasi menangani plat dan pipa panjang, **kedalaman yang direkomendasikan dan dijadikan acuan rancangan adalah lima tingkat: gudang → zona → row → rak → level → bin**, dengan **rak panjang** sebagai tipe lokasi utama untuk pipa/profil/plat dan **lantai** untuk barang berat. Hierarki tetap mendukung gudang kecil yang berhenti di dua tingkat, sehingga keputusan ini tidak memaksa struktur seragam. Acuan ini **dapat diubah** bila pemetaan fisik gudang nyata berbeda, dan perubahan itu tidak membongkar model data karena kedalaman lokasi bersifat dinamis.

**`INV-08` — Tipe dan kapasitas lokasi fisik dikelola penuh (CRUD) oleh bengkel:** master lokasi bukan data yang dipasang sekali oleh vendor. Petugas berizin (kepala gudang) dapat **membuat, membaca, mengubah, dan menonaktifkan** setiap tingkat lokasi beserta tipe dan kapasitasnya. Yang dapat dibuat/diubah: nama dan kode tiap tingkat (zona/row/rak/level/bin), **tipe lokasi** (bin, rak panjang, lantai, area remnant, karantina, staging), dan **kapasitas**: qty maksimum, berat maksimum, serta dimensi/panjang maksimum — termasuk bila kapasitas berbeda per level dalam rak yang sama. Perubahan kode lokasi wajib menyimpan riwayat karena label fisik di rak cetak/tempel; mengganti kode tidak mengubah identitas lokasi, sehingga stok yang ada tidak "hilang lokasi". Mengubah tipe/kapasitas yang membuat stok lama melanggar batas **tidak menghapus atau memindahkan stok secara diam-diam**: sistem menandai pelanggaran dan menyediakan daftar kerja perapian. Tipe lokasi juga menyimpan **aturan item** yang boleh masuk (mis. pipa/profil hanya rak panjang), dan aturan ini dapat diatur dari sisi lokasi maupun sisi item. Penghapusan fisik lokasi tidak disediakan; lokasi ditutup (nonaktif) hanya bila tidak berisi stok, dengan riwayat tetap utuh (`REP-22`).

**`INV-08` — Kebijakan wajib-posisi: seluruh item** (diputuskan owner): tidak ada item yang boleh disimpan tanpa lokasi. Setiap penerimaan, hasil produksi yang masuk stok, retur, sisa remnant, dan hasil transfer **wajib** menunjuk lokasi pada saat barang masuk; transaksi tanpa lokasi **ditolak**, bukan disimpan sebagai `unlocated`. Ini berlaku untuk semua jenis item, termasuk barang kecil bernilai rendah dan bahan yang dikonsumsi cepat, supaya tidak ada stok "hilang" di gudang dan opname tetap dapat dipertanggungjawabkan.

Konsekuensi yang harus diterima agar aturan ini tidak menghambat operasional: (a) harus tersedia **lokasi default per item** (dan per gudang) supaya penerimaan cepat tidak menuntut pilih lokasi berulang kali; (b) penerimaan borongan/cepat boleh memakai satu lokasi penampung (`staging`) **berbatas waktu**, tetapi stok staging tetap berlokasi sah dan **wajib** dirapikan ke lokasi tetap dalam tenggat yang disahkan; (c) barang yang belum selesai diidentifikasi tetap masuk **lokasi karantina berlabel**, bukan tanpa lokasi. Karena tidak lagi ada penampung `unlocated`, laporan `REP-22` berfokus pada **okupansi, pelanggaran kapasitas, dan barang yang masih di staging melewati tenggat**, bukan pada daftar item tanpa lokasi. Pengecualian wajib-posisi (bila nanti diperlukan, mis. barang langsung habis terpakai di lokasi kerja tanpa pernah masuk stok) merupakan **keputusan yang perlu disahkan ulang**, bukan bawaan sistem.

## 11. Engineering, produksi, dan pekerjaan kendaraan

### 11.1 Struktur pekerjaan

**FAB-01:** satu project/job dapat memiliki kendaraan, SO, beberapa WO, tahap, tugas, production order, dan pemasangan. Contoh routing: ukur/desain → cutting → bending → welding → machining → finishing/coating → assembly → pemasangan → QC → road test yang diizinkan → serah terima.

**FAB-02:** BOM bertingkat dan berversi untuk produk standar maupun custom; material utama, consumable, komponen beli, subassembly, estimasi scrap/yield. BOM/routing yang dirilis disalin sebagai snapshot ke order. Perubahan master tidak mengganti kebutuhan job berjalan.

**FAB-03:** lampiran gambar/CAD/PDF, ukuran/toleransi, catatan revisi, checklist keselamatan dan fitment. ERP menyimpan versi dan approval desain; tidak diklaim sebagai mesin CAD atau alat sertifikasi keselamatan kendaraan.

**FAB-04:** penjadwalan berdasarkan work center, mesin/bay, shift, skill, kapasitas, dependensi tahap, kedatangan material dan tanggal janji. Tampilkan antrean, bottleneck, beban kapasitas dan keterlambatan; override prioritas diaudit.

### 11.2 Pencatatan aktual

**FAB-05:** job card mencatat penanggung jawab, mulai/selesai, qty hasil, progress berbasis tahap, foto, blocker, material, jam kerja dan QC. Persentase progress tidak otomatis mengakui pendapatan.

**FAB-06:** timesheet per orang/job/tahap dengan approval; waktu produktif, setup, idle, rework dan lembur dibedakan. Cegah jam bertumpuk untuk orang yang sama kecuali kebijakan pembagian waktu eksplisit. Tarif costing bertanggal disimpan snapshot dan terpisah dari izin melihat gaji.

**FAB-07:** pemakaian mesin/consumable langsung dan overhead dialokasikan dengan dasar yang dapat diaudit: jam tenaga kerja, jam mesin, luas/berat atau driver/SKF yang sesuai. Actual, applied overhead dan selisih under/over-absorption terlihat; tidak membebankan listrik/depresiasi dua kali.

**FAB-08:** subkontrak coating, bubut, laser cutting dan jasa lain menggunakan PO jasa; material dikirim tetap terlacak sebagai milik bengkel di vendor; hasil kembali melalui pemeriksaan, dengan reject/rework dan tagihan vendor terkait job.

**FAB-09:** hasil produksi masuk layer barang jadi dengan biaya material + tenaga kerja langsung + overhead produksi yang diperbolehkan + subkontrak. Produksi parsial membagi biaya berdasarkan hasil/ekuivalen yang disetujui, menyisakan WIP belum selesai. Hindari pembebanan seluruh WIP ke unit pertama.

### 11.3 Quality, serah terima, dan garansi

**FAB-10:** QC penerimaan, in-process dan final memiliki checklist sesuai produk: dimensi, material, welding inspection, finishing, fitment, torque, elektrikal dan tes fungsi bila relevan. Nilai ukur, lampiran, pemeriksa, tanggal dan hasil lulus/gagal wajib tercatat. Checklist keselamatan disahkan kepala teknis; ERP tidak menggantikan penilaian kompeten.

**FAB-11:** nonconformance/rework mengacu defect, penyebab, tanggung jawab internal/vendor, material/jam ulang dan biaya. Status gagal memblokir tahap/serah terima terkait sampai dilepas oleh pihak berwenang.

**FAB-12:** delivery/serah terima mencatat hasil final, dokumen pelanggan, foto, persetujuan, garansi, sisa kewajiban pembayaran dan pengecualian kredit yang disetujui. **Serah terima tidak diselesaikan tanpa checklist inspeksi akhir (`FAB-13`) lengkap dan dikonfirmasi penerima.** Pemindahan biaya WIP ke HPP hanya sekali sesuai peristiwa pengakuan yang disahkan.

**FAB-13 — Checklist inspeksi akhir dan penyerahan (post-work inspection):** setelah pekerjaan selesai, sebelum kendaraan diserahkan, dijalankan **checklist inspeksi akhir** dari master yang sama dengan inspeksi awal (`VEH-02A`), sehingga butir yang diperiksa banding setara. Checklist akhir memuat: butir pekerjaan yang diselesaikan, hasil QC `FAB-10`/`FAB-11` (termasuk hasil ukur, torque, tes fungsi, uji kelistrikan, kebocoran), **perbandingan kondisi awal vs kondisi akhir** per butir, foto hasil akhir, pemasangan part tercatat, serta sisa pekerjaan atau rekomendasi.

Setiap **cacat baru** yang tidak ada pada kondisi awal wajib ditutup sebelum serah terima: diperbaiki, atau — bila memang di luar lingkup/disetujui — dicatat sebagai **pengecualian yang disetujui pelanggan** secara eksplisit, bukan diabaikan. Cacat yang sudah ada sejak awal dan tidak diperbaiki tetap menjadi tanggung jawab pelanggan dan dinyatakan demikian. **Penyerahan kendaraan diblokir** bila ada butir QC berstatus gagal (`FAB-11`), checklist akhir belum lengkap, atau item belum ditandatangani/dikonfirmasi penerima. Serah terima mencatat nama dan tanda tangan penerima, tanggal/jam, odometer akhir, tingkat BBM, perlengkapan yang dikembalikan (`VEH-03`), dokumen garansi (`WAR-01`) dan sisa kewajiban pembayaran/gate DP (`SAL-09`). Checklist awal dan akhir tersimpan permanen sebagai bukti; pertanyaan "siapa menanggung kerusakan ini" harus dapat dijawab dari kedua dokumen tanpa rekonstruksi manual.

**Kewenangan penanda tangan (disahkan owner):** checklist inspeksi akhir **ditandatangani kepala bengkel** sebagai pihak yang bertanggung jawab atas mutu dan keputusan pelepasan unit. Bila kepala bengkel tidak hadir (di luar jam kerja, cuti, atau dinas), pelepasan dapat dilakukan **pejabat sementara/PLT kepala bengkel** yang ditunjuk resmi (`ORG-01`), bukan mekanik pelaksana, dan penunjukan itu tercatat bertanggal. Bila keluaran unit mendesak dan tidak ada pejabat sementara, itu menjadi **exception berizin dengan alasan dan approval** yang tercatat, bukan dianggap pelepasan normal. **Tanda tangan digital menggunakan kebijakan yang sama dengan `VEH-02A`** dan setara dengan tanda tangan basah. Tanda tangan pelanggan/penerima juga boleh digital, terikat pada identitas, waktu, dan versi dokumen.

**FAB-14 — Check-out alat dari karo:** kebijakan "**karo gratis sampai alat kembali**" (`VEH-02B`) dijalankan lewat satu langkah **check-out** yang melepas alat dari karo dan sekaligus menutup penahanan. Check-out memuat: nomor karo/alat, unit penampung dan job/WO, tanggal/jam alat dilepas, kondisi alat saat dilepas, kondisi karo saat alat dilepas (mengacu checklist akhir `FAB-13` bila karo berupa kendaraan: ada/tidak baret atau kerusakan yang muncul selama alat tertahan), petugas pelepasan, foto sebelum/sesudah, dan tanda tangan **kepala bengkel** (atau PLT-nya) serta pelanggan/kuasanya bila karo milik/terkait pelanggan, dengan kebijakan tanda tangan yang sama dengan `VEH-02A`.

Setelah check-out: **alat bebas dialokasikan kembali** ke job/karo lain, status "tertahan di karo" berakhir, dan **check-out inilah yang memicu aturan biaya**. Selama belum ada check-out, **karo pengganti maupun perbaikan tidak ditagihkan** meskipun karo harus diganti lebih dari sekali (`VEH-02B`). Setelah check-out, perpanjangan karo atau pemakaian alat pada karo berikutnya **kembali mengikuti kebijakan biaya**, dengan penggantian karo berulang tetap dapat dilakukan tanpa biaya sampai alat benar-benar kembali. Check-out yang melepas alat tanpa menutup item checklist (bila karo berkendaraan), atau sebaliknya menutup job tanpa melepas alat, diblokir sebagai transisi tidak lengkap. Riwayat pasang/lepas per nomor seri alat tersimpan, sehingga bisa dibuktikan alat mana berada di karo mana pada tanggal berapa.

**WAR-01:** klaim garansi mengacu job, produk/serial dan syarat garansi saat penjualan; inspeksi, keputusan cover/tolak, perbaikan/penggantian, supplier recovery, biaya dan kepuasan. Biaya garansi tampil pada periode pembukuan dan lifetime profitability job asal tanpa mengubah invoice lama diam-diam.

## 12. Job costing, anggaran, dan profitabilitas

**JOB-01 — Dimensi:** setiap pendapatan/biaya relevan ditautkan ke perusahaan, cabang, cost/profit center, project/job, kendaraan, WO/tahap dan kategori biaya sejauh berlaku. Biaya umum boleh tanpa job tetapi masuk cost center yang jelas; sistem tidak memaksa kendaraan pada transaksi payroll seluruh perusahaan.

**JOB-02 — Empat pandangan biaya:**

1. Baseline estimate saat penawaran diterima.
2. Revised budget setelah change order disetujui.
3. Committed cost dari PO/subkontrak belum terealisasi, net dari bagian yang sudah menjadi actual.
4. Actual cost dari posting serta estimate-to-complete (ETC) untuk pekerjaan tersisa.

```text
EAC = actual cost + ETC
Forecast margin = pendapatan kontrak yang disetujui − EAC
Budget variance = revised budget − actual cost
```

ETC memasukkan komitmen tersisa yang relevan; jangan menambahkan committed cost dua kali ke EAC. Revenue forecast terpisah dari revenue recognized.

**JOB-03 — Tingkat margin:** pendapatan neto → biaya material landed → tenaga kerja langsung → subkontrak → overhead produksi → gross profit → alokasi beban operasional → management net contribution. Alokasi beban operasional untuk analisis tidak otomatis mengkapitalisasi biaya ke persediaan/WIP.

**JOB-04:** budget per job, akun, periode, tahap dan cost center; alert/block overbudget sesuai ambang. Versi dan dasar alokasi overhead/SKF disimpan. Perubahan basis alokasi berlaku pada periode target yang terbuka, tidak menggeser laporan periode tertutup.

**JOB-05:** laporan profitability dapat dibuka per job, kendaraan, pelanggan, paket produk, mekanik/tim dan cabang. Kinerja mekanik menampilkan konteks jenis pekerjaan, rework dan jam, bukan menyamakan semua omzet sebagai hasil individu.

## 13. Akuntansi, kas, pajak, dan closing

### 13.1 Prinsip pengakuan

**FIN-01:** akrual dan double-entry; setiap posting memiliki total debit = kredit, tanggal dokumen, tanggal posting, sumber, mata uang/kurs, dimensi dan reversal link. Mapping akun wajib lengkap; posting gagal dengan pesan jelas jika belum lengkap.

**FIN-02 — DP dan pendapatan:** DP pelanggan default kewajiban uang muka, bukan pendapatan. Barang retail diakui ketika kontrol diserahkan sesuai kebijakan; pekerjaan custom default pada serah terima/acceptance kewajiban terkait. Progress billing bukan otomatis pendapatan. Pengakuan over-time hanya diaktifkan untuk kontrak yang memenuhi kebijakan yang disahkan dan memiliki pengukuran progress serta jurnal contract asset/liability yang jelas.

**FIN-03 — WIP:** material, tenaga kerja dan overhead produksi job yang memenuhi syarat dikumpulkan di WIP sampai peristiwa pelepasan biaya. Pemakaian material tidak sekaligus menjadi beban dan WIP. Kerugian abnormal/biaya tidak memenuhi kapitalisasi dipisahkan.

**FIN-04 — Pajak:** kode, tarif dan tanggal berlaku; inclusive/exclusive; recoverable/nonrecoverable; pemotongan/pemungutan dan bukti; invoice/credit note; laporan rekonsiliasi pajak. Tarif tidak di-hardcode dalam PRD. Perlakuan DP dan saat terutang pajak dapat berbeda dari pengakuan pendapatan; engine pajak dan jurnal harus mendukung perbedaan tersebut.

### 13.2 Matriks jurnal minimum

Retur pemasok, refund, write-off dan cost adjustment harus memiliki posting rules tersendiri sebelum UAT; tidak cukup jurnal manual tanpa referensi sumber.

### 13.3 Operasi finance

**FIN-06:** AR/AP open item, due date, aging, partial payment, alokasi many-to-many, credit note, write-off approved, statement partner, reminder penagihan dan batas kredit. Saldo historical aging direkonstruksi berdasarkan transaksi pada cutoff, bukan status pembayaran hari ini.

**FIN-07:** kas kecil imprest/non-imprest, uang muka operasional, pertanggungjawaban, reimbursement, transfer bank, rekening owner/prive/modal yang terpisah. Pembayaran bank dapat diusulkan/disetujui tanpa mengasumsikan transfer otomatis ke bank.

**FIN-08:** impor rekening koran CSV/XLSX dengan preview/mapping, identitas impor untuk deduplikasi, match satu/banyak, biaya bank, bunga dan unmatched. Status reconciled dapat dibuka dengan approval dan audit; tidak mengubah sumber tanpa reversal.

**FIN-09:** jurnal manual dengan approval, recurring journal, accrual, amortisasi prepaid, kurs, koreksi, dan lampiran. Akun kontrol stok/AR/AP/WIP tidak boleh diubah manual tanpa mekanisme subledger yang konsisten; gunakan dokumen penyesuaian khusus.

**FIN-10:** checklist kas/bank, AR/AP, GRNI/accrual, estimasi landed cost, inventaris, WIP, payroll, overhead, depresiasi, pajak dan jurnal penyesuaian → rekonsiliasi → approval → period lock. Tahun tutup mengalihkan hasil ke saldo laba sesuai kebijakan, dengan jejak yang dapat diaudit.

**FIN-11:** period lock diperiksa di transaksi yang sama saat posting/reversal. Pembukaan ulang dibatasi, memerlukan alasan dan persetujuan; snapshot laporan sebelumnya tetap tersimpan. Tanggal posting selalu terlihat bila berbeda dari tanggal dokumen.

**FIN-12 — Termin, jatuh tempo, dan aging:** setiap tagihan vendor/pelanggan menyimpan basis tanggal, jumlah hari, tanggal jatuh tempo, hari diskon bila ada, dan status (`belum jatuh tempo`, `jatuh tempo`, `terlambat`). Jatuh tempo **tidak** dipengaruhi tanggal input data, tanggal posting jurnal, maupun tanggal cetak; tanggal dokumen dan tanggal posting selalu ditampilkan terpisah bila berbeda. Aging (0-30/31-60/61-90/>90) direkonstruksi as-of tanggal cutoff, bukan dari status pelunasan hari ini (FIN-06). Hari jatuh tempo memakai kalender operasional; hari libur tidak memindahkan jatuh tempo kecuali kebijakan disahkan. Termin hanya mengatur **kapan dibayar**; tidak mengubah aturan kapan utang diakui.

**FIN-13 — Pengakuan utang vendor (GRNI):** utang diakui dari **GRN** saat barang diterima (debit persediaan/WIP, kredit GRNI/utang belum ditagih) dan diselesaikan saat invoice vendor di-match (three-way match, PUR-07): GRNI didebit, utang vendor dikredit sebesar nilai tagihan. Invoice sebelum GRN dicatat tagihan belum matched tanpa menambah qty stok. Perbedaan nilai GRN vs tagihan (ongkir, kurs, harga) masuk akun/penyesuaian yang terlihat; di atas toleransi memblokir pembayaran sesuai kebijakan (lihat juga PUR-12 dan §9.3).

**FIN-14 — Pengakuan piutang pelanggan:** piutang diakui saat penjualan/pekerjaan diakui (invoice pada pengakuan jual, atau progress invoice sebelum pengakuan sebagai contract liability), bukan saat dokumen dibuat. DP yang diterima sebelumnya mengurangi eksposur lewat alokasi (uang muka pelanggan → piutang), tetap dapat ditelusuri, dan tidak diakui sebagai pendapatan dua kali (FIN-02, matriks §13.2). Retur/credit note membalik revenue/pajak dan HPP sesuai dokumen asal (FIN-05).

**FIN-15 — Alokasi dan pembayaran:** satu penerimaan boleh dialokasikan ke beberapa invoice; satu invoice boleh dibayar bertahap; kelebihan bayar menjadi credit pelanggan/uang muka atau refund dengan approval. Pembayaran diterima hari ini atas invoice yang jatuh tempo sebelum cutoff tetap boleh ditagih, tetapi **aging as-of cutoff tidak berubah** karena peristiwa setelah cutoff (FIN-06, UAT-21). Alokasi tidak melebihi nominal penerimaan atau invoice; pembatalan/reversal pembayaran menghitung ulang status gate DP (SAL-11).

**FIN-16 — Piutang macet, write-off, dan limit kredit:** penagihan berjenjang dengan reminder; daftar overdue per pelanggan dan sales penanggung jawab; pelanggan melewati limit atau menunggak dapat ditahan (`hold`) untuk komitmen baru (CUS-02), sementara pelunasan dan penyelesaian akuntansi tetap tersedia. Write-off hanya dengan approval, alasan, dan jejak audit; piutang tidak dihapus hanya karena lama. Perhitungan limit kredit mempertimbangkan saldo, due date, DP belum dialokasikan dan status hold.

**FIN-17 — Termin pelanggan:** selain DP wajib 50% pelanggan Umum (SAL-09–12), termin pelanggan mengikuti master MD-08/MD-09 dengan default **COD atau CBD** dan tanpa asumsi kredit 30 hari kecuali disetujui. Term pelanggan disnapshot ke SO/penawaran; mengubah kategori atau master tidak melemahkan gate DP order berjalan (CUS-04). Jadwal pelunasan sisa harus dinyatakan dalam penawaran; kewajiban DP 50% tidak otomatis menyetujui kredit untuk sisanya (SAL-05, SAL-12).

**FIN-18 — Denda, bunga, dan selisih kurs:** denda/bunga keterlambatan dicatat pada akun terpisah, bukan menambah pokok utang/piutang tanpa dokumen; selisih kurs atas utang/piutang valuta asing direvaluasi pada tanggal pelaporan sesuai kebijakan finance; pembayaran sebagian memakai kurs transaksi dan selisihnya terlihat.

**FIN-19 — Saldo awal dan data historis utang/piutang:** migrasi memuat saldo awal utang/piutang beserta tanggal dokumen asal dan jatuh temponya agar aging as-of cutover benar; pembayaran historis sebelum cutover tidak dipakai menghitung ulang due date; item tanpa dokumen asal tetap dapat dialokasikan ke pembayaran berikutnya.

**FIN-20 — Rekonsiliasi kontrol:** saldo akun kontrol AR/AP/WIP direkonsiliasi berkala dengan total subledger open item; selisih dijelaskan per item, bukan lewat jurnal manual tanpa referensi; jurnal manual ke akun kontrol ditolak kecuali memakai dokumen penyesuaian khusus (FIN-09).

**FIN-21 — Draf boleh berubah, dokumen posted tidak:** selama pekerjaan custom masih berjalan dan invoice masih berstatus **draf/sementara**, isinya **boleh direvisi** mengikuti perubahan harga (`SAL-14`) tanpa memerlukan reversal, karena draf **belum menjadi transaksi akuntansi**: belum ada entri jurnal, belum mengubah AR/WIP, dan belum mengikat pajak maupun aging (`FIN-14`). Setiap revisi draf tetap menyimpan **riwayat versi** (nomor versi, waktu, penyusun, alasan) agar perjalanan harga dapat ditelusuri, dan wajib memakai ulang nomor dokumen yang sama — bukan membuat invoice baru tiap perubahan. Penomoran invoice tidak boleh melompat-lompat hanya karena draft diubah.

Sebaliknya, invoice yang sudah **posted/final** (sudah diakui sebagai piutang dan/atau pendapatan) **tidak dapat diedit**, sekalipun pekerjaan belum selesai sepenuhnya. Perubahan setelah posting hanya lewat dokumen koreksi resmi: **credit note** untuk penurunan, **debit note/invoice tambahan** untuk kenaikan, atau `change order` yang menghasilkan invoice tambahan — semuanya bernomor, berreferensi dokumen asal, dan tidak menimpa histori (`FIN-05`). Batas kapan draf berubah menjadi final ditetapkan oleh **peristiwa serah terima/acceptance** (`SAL-13`, `FIN-02`), bukan oleh kehendak pengguna; sebelum peristiwa itu draf cair, sesudahnya terkunci. Secara teknis, transisi dari revisi draf ke posting final harus idempoten dan terlindung dari dua revisi/posting bersamaan pada invoice yang sama.

Contoh sederhana: SO Rp20.000.000 dengan DP Rp10.000.000 dibayar. Saat bongkar ditemukan rangka yang perlu diperkuat (revisi +Rp3.000.000) lalu pelanggan menambah lampu (+Rp1.000.000). Selama unit belum diserahkan, **satu** invoice draft hanya bergerak versi: Rp20.000.000 → Rp23.000.000 → Rp24.000.000, dan minimum DP ikut naik menjadi Rp12.000.000 sehingga timbul kekurangan Rp2.000.000 yang harus dibayar sah sebelum bagian pekerjaan lanjutan dirilis (`SAL-11`). Saat serah terima, draft diposting final pada Rp24.000.000; setelah itu perubahan apa pun hanya lewat credit/debit note.

### 13.4 Petty cash, pengajuan dana dan pertanggungjawaban

**PC-01 — Master kas kecil:** kode/nama dana, perusahaan/cabang, pemegang kas/custodian, akun buku besar, metode imprest/non-imprest, plafon, saldo minimum pengisian ulang, batas transaksi, kategori pengeluaran diizinkan, rekening sumber dan matriks approval. Setiap dana mempunyai buku kas sendiri; akses pengaju, approver dan pembayar dipisahkan. Metode imprest menggunakan plafon dana tetap dengan pengeluaran dicatat saat terjadi dan pengisian ulang sebagai transfer, bukan mengakui beban kedua kali.

**PC-02 — Pengajuan dan pencairan:** karyawan mengajukan tujuan, rincian/estimasi, nominal, tanggal dibutuhkan, job/cost center, calon penerima dan lampiran → atasan/penanggung jawab budget → finance sesuai ambang → approved → pembayaran posted dengan bukti → settlement. Status rejected, cancelled, partial disbursement, outstanding dan settled tersedia. Persetujuan belum mengurangi saldo kas atau mencatat beban; hanya pencairan posted yang melakukannya. Dukung pengeluaran langsung dengan bukti maupun uang muka/kasbon operasional yang harus dipertanggungjawabkan. Tolak kas negatif, pembayaran melebihi sisa approval dan pemecahan pengajuan untuk melewati ambang; pengajuan terkait dinilai bersama sesuai kebijakan.

**PC-03 — Pertanggungjawaban (LPJ):** setiap uang muka mempunyai pemegang, deadline, rincian bukti/nota, tanggal, pemasok/penerima, kategori/akun, pajak bila berlaku, job/cost center, nominal disetujui dan alasan penolakan. Lebih dana wajib dikembalikan dengan bukti; kurang dana menjadi reimbursement/kewajiban setelah disetujui, bukan langsung dianggap sudah dibayar. LPJ parsial menyisakan saldo outstanding. Tidak boleh memakai satu bukti untuk klaim berulang; deteksi nomor/tanggal/vendor/nominal dan konfirmasi kandidat duplikat, dengan audit bila memang transaksi berbeda. Saldo dan umur uang muka memengaruhi izin pengajuan baru sesuai kebijakan, bukan dihapus saat melewati deadline.

**PC-04 — Reimbursement dan pembelian barang:** pengeluaran pribadi karyawan masuk klaim → verifikasi bukti → approval → utang reimbursement → pembayaran. Bedakan dari pinjaman pribadi LN-01 dan dari kasbon operasional yang dananya sudah diberikan perusahaan. Pembelian persediaan/aset lewat petty cash tetap menggunakan dokumen penerimaan/kapitalisasi dan utang/clearing yang sesuai; tidak boleh dibukukan sebagai beban kantor untuk melewati stok. Jika dokumen pembelian sudah mengakui biaya/aset, LPJ hanya menyelesaikan akun perantara; tidak mengakui perolehan dua kali.

**PC-05 — Posting minimum dan contoh:** berikut contoh tanpa pajak, dengan pencatatan pengeluaran saat terjadi.

| Peristiwa | Debit | Kredit | Kontrol |
| --- | --- | --- | --- |
| Pembentukan/pengisian ulang kas kecil | Kas kecil | Bank | Transfer aset, bukan beban |
| Pencairan kasbon operasional | Uang muka operasional karyawan | Kas kecil/bank | Bukan pinjaman pribadi dan belum menjadi beban |
| Pengeluaran langsung atau LPJ beban yang disetujui | Beban/WIP yang memenuhi syarat | Kas kecil untuk langsung; uang muka operasional untuk LPJ | Referensi nota/job, bukan keduanya sekaligus |
| Pengembalian sisa kasbon | Kas kecil/bank | Uang muka operasional karyawan | Mengurangi outstanding tepat sekali |
| Bagian biaya sah di atas uang muka | Beban/WIP yang memenuhi syarat | Utang reimbursement | Pembayaran kemudian Dr utang reimbursement, Cr kas/bank |

Contoh: dana kas kecil Rp1.000.000 → kasbon Rp300.000 → kas fisik Rp700.000 dan uang muka Rp300.000. LPJ sah Rp250.000 serta pengembalian Rp50.000 menghasilkan kas Rp750.000, uang muka nol, beban Rp250.000. Replenishment Rp250.000 mengembalikan kas menjadi Rp1.000.000 tanpa menambah beban lagi. Semua penerimaan/pengeluaran memakai sequence, period lock dan idempotensi; dana bersama tidak boleh dicairkan ganda oleh pengguna bersamaan.

**PC-06 — Cash count, closing dan serah terima:** hitung kas per pecahan, bandingkan buku kas dengan fisik, catat selisih dan investigasi/approval akun koreksinya. Untuk kontrol imprest, tampilkan kas fisik + uang muka outstanding + pengeluaran sah yang belum direplenish terhadap plafon; ini kontrol pertanggungjawaban, bukan alasan menyamakan nota pengeluaran dengan kas di neraca. Pergantian custodian memerlukan saldo awal/akhir, daftar uang muka, berita acara dan persetujuan kedua pihak. Penutupan dana mengembalikan sisa kas ke bank dan menyelesaikan outstanding. Laporan mencakup mutasi, pengeluaran per kategori/job, aging LPJ, reimbursement, replenishment dan selisih kas.

## 15. SDM, payroll, aset, dan maintenance

**HR-01:** karyawan, kontrak, jabatan/departemen, skill/sertifikasi, shift, work calendar, libur umum/departemen, absensi, koreksi, cuti/kuota, lembur approved, timesheet, apresiasi, pinjaman/cicilan dan dokumen karyawan.

**HR-02:** payroll periodik dengan komponen penghasilan/potongan, prorata, BPJS/PPh dan tanggal berlaku sesuai aturan yang disahkan; preview → approval → posting → payslip → pembayaran. Koreksi payroll posted memakai adjustment. Payroll dan timesheet berhubungan tetapi tidak diasumsikan identik.

**HR-02A — Komponen, slip, dan penyelesaian keberatan:** setiap komponen payroll diklasifikasikan sebagai penghasilan, potongan, atau informasi saja; komponen informasi tampil di slip tetapi tidak mengubah take-home pay, sehingga tidak boleh dijumlahkan sebagai penghasilan. Slip kerja memuat periode, run, frekuensi (mingguan/bulanan), dasar perhitungan (hari/jam hadir, tarif, jam lembur sah, cicilan) dan komponen bertanggal. Karyawan berhak mengajukan **keberatan/koreksi slip** dalam tenggat yang disahkan; keberatan membuat kasus dengan status terbuka → diperiksa HR/payroll → diterima/ditolak beralasan → bila disetujui diselesaikan lewat run yang belum dikunci atau adjustment terhubung, bukan mengedit slip posted. Menahan pembayaran yang tidak disengketakan hanya karena sebagian slip dipersoalkan dilarang; hanya bagian yang dikoreksi yang disesuaikan. Riwayat slip tidak dihapus saat karyawan keluar; akses slip hanya pemilik dan HR berizin, dan kepala bengkel tetap tidak melihat nominal gaji.

**HR-03:** posting payroll direkonsiliasi ke labor applied pada job agar gaji tidak menjadi biaya dua kali. Idle time, lembur nonproduksi dan selisih tarif terpisah. Simulasi payroll tidak memengaruhi jurnal.

**HR-03A — Frekuensi payroll mingguan dan bulanan:** sistem mendukung sekurang-kurangnya dua siklus payroll paralel untuk pekerja yang sama tanpa menggandakan gaji atau potongan. Setiap pekerja memiliki satu jadwal payroll utama bertanggal berlaku: **mingguan** (mis. tenaga harian/kasual/proyek) atau **bulanan** (mis. staf tetap), dan satu peristiwa ekonomi hanya boleh masuk ke satu run. Gaji pokok hanya dibayarkan pada run yang memuat periode gajinya; run lain hanya memuat komponen yang memang menjadi hak periode itu, sehingga mingguan dan bulanan tidak menghitung pokok dua kali.

Cutoff setiap run eksplisit dan tidak boleh tumpang tindih unit kerjanya: absensi, lembur yang disahkan (`HR-07`–`HR-09`), cuti tidak berbayar, cicilan pinjaman (`LN-03`), potongan lain dan komponen variabel diambil dari periode cutoff run tersebut dan ditandai terpakai, tidak dapat diklaim run lain. Sumber frekuensi adalah **profil karyawan**: setiap pekerja ditandai mingguan atau bulanan pada skema payroll-nya (`EMP-01A`, `EMP-04`), sehingga run yang relevan ditentukan dari profil, bukan dipilih bebas saat menghitung payroll. Pemetaan jadwal mingguan ke bulanan membagi periode bulanan menjadi minggu kerja yang tetap (mis. 4+1 atau sesuai kalender kerja yang disahkan), bukan pembagian arbitrer; sisa hari diperlakukan sebagai periode pelengkap yang disahkan.

Lembur yang jatuh pada periode mingguan dan belum disahkan saat cutoff dapat ditahan dan dibayar pada run berikutnya dalam jadwal yang sama, atau dipindahkan ke run bulanan menurut kebijakan yang disahkan; perlakuan itu wajib eksplisit, tidak boleh hilang atau terhitung dua kali. Bila satu pekerja berpindah dari mingguan ke bulanan (atau sebaliknya) pada tanggal efektif tertentu, run peralihan memuat hak sampai tanggal perpindahan dan run berikutnya mulai dari tanggal tersebut; tidak ada periode tanpa slip atau slip ganda untuk hari yang sama. Potongan pinjaman mengikuti frekuensi run aktual (cicilan mingguan atau bulanan) dengan batas potongan per pembayaran, dan run periode lebih panjang boleh memuat lebih dari satu cicilan sepanjang limit tetap terjaga. Jika payroll bulanan posted lebih dahulu, lembur mingguan yang belum disahkan masuk sebagai adjustment atau run susulan terhubung, bukan perhitungan ulang periode lama.

Frekuensi, hari cutoff dan jadwal bayar untuk tiap pekerja memerlukan keputusan owner/HR/finance sebelum produksi; angka default (misalnya hari cutoff) tidak ditanam di kode.

**HR-04 — Master jadwal kerja:** kode/nama jadwal, cabang/departemen, pola hari kerja dan hari istirahat, shift, jam mulai/selesai, interval istirahat berbayar/tidak berbayar, toleransi keterlambatan, target jam normal serta tanggal berlaku. Dukung jadwal tetap, roster bergilir, shift lintas tengah malam, dan kalender libur umum maupun departemen. Batas jam normal/lembur mengikuti kebijakan yang disahkan dan aturan ketenagakerjaan yang berlaku; bukan angka jam yang ditanam permanen di kode.

**HR-05 — Roster dan perubahan jadwal:** penugasan jadwal per karyawan/periode, pengganti shift, tukar shift dengan approval dan notifikasi. Urutan penentuan jelas: penugasan khusus karyawan pada tanggal tersebut → roster karyawan → jadwal default departemen/cabang. Kalender libur, cuti dan izin diselesaikan secara eksplisit saat publish roster, tidak saling menimpa diam-diam. Tolak interval kerja bertumpuk untuk orang yang sama; perubahan jadwal berversi tidak menghitung ulang absensi/payroll posted. Work center/bay scheduling FAB-04 memakai ketersediaan roster, cuti dan skill, bukan kalender mesin saja.

**HR-06 — Kehadiran dan jam normal:** simpan timestamp masuk/keluar/istirahat, asal pencatatan, koreksi approved, terlambat, pulang awal, izin/sakit, absen tanpa keterangan dan punch yang belum lengkap. Shift malam memakai identitas shift dan tanggal mulai meskipun selesai esok hari; pecah interval menurut tanggal kalender untuk tarif hari libur bila aturan mengharuskan. Punch hilang menjadi exception untuk diperiksa, bukan otomatis dianggap nol jam atau satu shift penuh. Jangan menghitung seluruh waktu antara clock-in dan clock-out sebagai kerja produktif maupun lembur.

**HR-06A — Penggantian pekerjaan saat absen dan lembur pengganti:** bila pekerja tidak masuk (sakit/izin/absen) atau sesi produksi gagal dan pekerjaan digantikan orang lain, catat penugasan pengganti terpisah beserta siapa yang digantikan, tahap/WO, dan jam yang benar-benar dikerjakan. Pembayaran mengikuti pekerja yang benar-benar bekerja, bukan rencana awal; jam pekerja yang tidak hadir diproses sebagai absensi/izin, bukan lembur. Lembur pengganti hanya sah bila diajukan dan disetujui sesuai `HR-07` oleh kepala bengkel/atasan langsung pengganti tersebut; tidak ada lembur otomatis karena mengambil alih tugas orang lain. Penggantian tidak boleh membuat dua orang dibayar untuk interval yang sama pada job yang sama; overlap ditolak atau didokumentasikan sebagai pekerjaan paralel yang berbeda dan sah. Kepala bengkel dapat menunjuk pengganti dengan alasan operasional, dan penugasan itu berjejak untuk perhitungan jam serta biaya job.

**HR-07 — Pengajuan dan realisasi lembur:** karyawan mengajukan dokumen lembur (boleh lewat self-service `SEC-04`) yang memuat karyawan, tanggal/interval rencana, alasan, job/WO/cost center, pemberi tugas, persetujuan/persetujuan pekerja sesuai ketentuan dan interval aktual berikut istirahat. Approval operasional berada pada atasan langsung/**kepala bengkel** pemilik pekerjaan, bukan HR dan bukan pembuat dokumen; creator tidak menyetujui dokumennya sendiri. Kepala bengkel dapat **menyetujui, menolak, atau mengembalikan untuk revisi** dengan alasan wajib saat menolak; approval hanya sah bila job/WO/cost center benar, interval tidak bertabrakan jadwal normal atau lembur lain, dan kebijakan lembur aktif. HR/payroll hanya menjalankan verifikasi dan penetapan durasi yang sah, bukan menggantikan keputusan operasional. Bedakan durasi diminta, disetujui, dikerjakan, serta durasi yang disahkan untuk payroll. Tolak duplikasi/overlap antardokumen untuk orang yang sama. Kerja melewati jadwal tanpa approval ditandai exception untuk penyelesaian HR, bukan otomatis dibayar atau otomatis dihapus. Prosedur lembur darurat memerlukan alasan dan pengesahan susulan tanpa menghilangkan catatan aktual.

Alur end-to-end yang mengikat: (1) karyawan mengajukan form lembur; (2) kepala bengkel/atasan langsung menyetujui atau menolak; (3) dokumen berstatus disetujui direkam aktual kerjanya; (4) HR/payroll menetapkan durasi sah; (5) **hanya durasi sah itu masuk ke perhitungan penggajian** sesuai `HR-08` dan `HR-09`, sekali saja; (6) penggajian berjalan pada siklus mingguan atau bulanan pekerja tersebut sesuai `HR-03A`.

**HR-08 — Perhitungan jam dan upah lembur:** durasi bersumber interval aktual terverifikasi dikurangi istirahat yang tidak dihitung bekerja; penyelesaian selisih rencana/approval/aktual harus eksplisit. Jam normal dan lembur tidak boleh menempati interval yang sama. Aturan hari kerja/hari istirahat/libur, dasar upah, multiplier bertingkat, pembulatan durasi, batas durasi dan komponen tunjangan berversi menurut tanggal berlaku serta disahkan HR/finance. Simpan menit aktual sebelum pembulatan dan rincian rumus per karyawan, bukan nominal lembur manual tanpa dasar. Contoh durasi: 18.00–21.00 dengan istirahat tidak dibayar 30 menit = 150 menit atau 2,5 jam; 22.00–02.00 esok hari dengan istirahat 30 menit = 210 menit atau 3,5 jam. Contoh ini menghitung durasi, bukan menetapkan tarif hukum.

**HR-08A — Dasar upah berversi untuk tarif lembur:** dasar upah lembur diturunkan dari **gaji pokok/komponen yang berlaku pada tanggal kerja dilakukan**, bukan tanggal pengajuan, persetujuan, atau tanggal bayar. Bila gaji karyawan naik di tengah periode (mis. kenaikan tanggal 1 sementara lembur dilakukan tanggal 20), lembur tanggal 20 memakai versi gaji yang berlaku saat itu. Turunan tarif harian/jam memakai penyebut yang disahkan HR/finance (mis. 1/25 atau 1/173) dan **penyebut itu wajib disahkan, bukan diasumsikan**; bila kebijakan berubah, berlaku hanya untuk kerja setelah tanggal efektifnya. Simpan pada setiap baris lembur: `employee_pay_rate_version_id`, dasar upah, penyebut, dan tanggal kerja, sehingga perhitungan dapat direproduksi walau gaji pokok sudah berubah. Selisih yang muncul karena koreksi versi gaji dihitung sebagai penyesuaian terhubung, bukan mengedit baris payroll posted (`HR-02A`, `HR-09A`).

**HR-09 — Hubungan lembur, job dan payroll:** durasi yang disahkan masuk payroll tepat sekali; distribusi timesheet beberapa job tidak boleh melebihi waktu orang tersebut. Rekam basis dan alokasi biaya lembur per job atau cost center nonproduksi, termasuk perlakuan premium lembur sesuai kebijakan kapitalisasi. Approval timesheet saja tidak menggantikan approval lembur. Koreksi setelah payroll posted melalui adjustment terhubung ke dokumen asal; periode lama tidak dihitung ulang diam-diam. Laporan harus dapat menjelaskan jam aktual → jam disahkan → tarif → upah → payroll → biaya job/overhead tanpa menggandakan biaya.

**HR-09A — Penautan durasi disahkan ke run mingguan/bulanan:** setiap durasi lembur yang disahkan menunjuk tepat satu run penggajian dan satu periode cutoff; sebelum terpakai ia berstatus *tersedia untuk payroll*, setelah masuk run berstatus *terpakai* dan tidak dapat diklaim run lain, termasuk bila run mingguan dan bulanan berjalan paralel. Run memuat hanya dokumen lembur yang tanggal kerja dan status sahnya berada di dalam cutoff run tersebut. Dokumen yang disahkan setelah cutoff mingguan ditahan untuk run mingguan berikutnya atau dipindahkan ke run bulanan menurut `HR-03A`, dan pemindahan itu tercatat, bukan disalin. Pembatalan dokumen lembur yang belum terpakai melepas durasi dari antrean; pembatalan setelah masuk run posted diselesaikan lewat adjustment terhubung, bukan menghapus baris payroll lama. Run bulanan tidak boleh memuat ulang lembur yang sudah dibayar lewat run mingguan untuk orang dan tanggal yang sama; laporan `REP-18` harus membuktikan total jam disahkan sama dengan total jam terbayar dalam satu periode rekonsiliasi.

### 15.1 Profil lengkap dan data kepegawaian

**EMP-01 — Identitas dan kontak karyawan:** bedakan nomor induk karyawan internal (NIP/kode karyawan) dengan NIK kependudukan. Karyawan memiliki ID permanen agar mutasi cabang/jabatan atau perubahan nama tidak membuat histori payroll baru yang terputus.

| Kelompok | Field yang tersedia | Aturan kelengkapan |
| --- | --- | --- |
| Identitas internal | Kode karyawan unik, nama lengkap sesuai identitas, nama panggilan, foto, status aktif | Kode dan nama wajib; foto sesuai kebijakan operasional |
| Identitas legal | Jenis identitas, NIK kependudukan untuk WNI, nomor paspor/izin yang relevan untuk WNA, lampiran terlindungi | Wajib sesuai status pekerja saat verifikasi onboarding; NIK WNI 16 digit disimpan string, tidak menjadi kode karyawan |
| Kelahiran dan profil | Tempat lahir, tanggal lahir, jenis kelamin, kewarganegaraan, status perkawinan, data tanggungan yang relevan untuk benefit/pajak | Tempat/tanggal lahir wajib; atribut lainnya dikumpulkan sesuai kebutuhan sah, bukan untuk akses diskriminatif |
| Alamat identitas | Jalan/kompleks, nomor bangunan/unit, RT/RW bila berlaku, desa/kelurahan, kecamatan, kabupaten/kota, provinsi, kode pos, negara | Lengkap sesuai dokumen/format negara; salin ke domisili bila sama tanpa menghilangkan jenis alamat |
| Alamat domisili | Komponen alamat lengkap yang sama, petunjuk alamat bila perlu | Terpisah dari alamat identitas; riwayat perubahan dapat ditelusuri |
| Kontak | HP/telepon, WhatsApp bila berbeda, email pribadi dan email kerja bila tersedia | Minimal satu nomor utama; email kerja tidak dipaksakan untuk pekerja tanpa akun email |
| Kontak darurat | Nama, hubungan, nomor telepon, alamat bila diperlukan | Minimal satu kontak darurat; bukan otomatis penerima gaji atau pemegang akses akun |
| Pendidikan/kompetensi | Pendidikan, keahlian, sertifikasi, penerbit, tanggal berlaku/expiry dan bukti | Dipakai penugasan pekerjaan/mesin; tidak mengganti persetujuan teknis QC |
| Skema dan frekuensi payroll | Skema payroll, **frekuensi gaji: mingguan atau bulanan**, periode/cutoff, jadwal bayar, tanggal efektif mulai berlaku, dan alasan perubahan | Wajib sebelum aktivasi payroll; satu jadwal utama aktif per pekerja pada satu waktu; perubahan bertanggal efektif dan berjejak, disahkan HR/finance |

**EMP-01A — Gaji pokok dan komponen tetap karyawan:** profil karyawan menyimpan gaji pokok bertanggal berlaku (nominal dan currency, mis. `Rp 4.500.000` per bulan atau `Rp 1.125.000` per minggu) beserta komponen tetap lain, tunjangan tetap, dan potongan tetap beserta tanggal mulai berlakunya. Gaji pokok disimpan sebagai nominal per periode frekuensi gaji pekerja, bukan satu angka bebas yang diambil dari dokumen; sistem menurunkan tarif harian/jam dari situ bila dibutuhkan (mis. 1/25 atau 1/173 sesuai ketentuan yang disahkan). Riwayat kenaikan disimpan sebagai versi bertanggal; mengubah gaji pokok tidak menulis ulang payroll yang sudah posted, dan berlaku mulai tanggal efektif pada run yang belum dikunci.

Gaji pokok hanya dibayarkan pada run yang memuat periode gajinya; run mingguan dan bulanan tidak menghitung pokok dua kali (`HR-03A`). Potongan tetap bulanan (mis. cicilan pinjaman bulanan) hanya diambil pada run frekuensi yang sesuai dan tidak diulang di run lain. Gaji pokok dan tarif adalah field sensitif dengan permission terpisah (`SEC-01`–`SEC-04`); tidak muncul di direktori umum, ekspor, atau tampilan kepala bengkel. Nominal di dokumen ini adalah contoh format, bukan usulan angka yang disahkan.

**EMP-02 — BPJS, pajak dan benefit:** field terpisah untuk nomor peserta BPJS Kesehatan dan BPJS Ketenagakerjaan, status pendaftaran/keaktifan, tanggal mulai/akhir, program yang diikuti, basis upah/iuran bertanggal dan dokumen verifikasi. Simpan NPWP/identitas pajak yang berlaku, status PTKP serta perubahan tanggungan dengan tanggal efektif dan izin sensitif. Jangan menyalin nomor dari satu program ke program lain. Kepesertaan belum selesai memiliki status `pending` dan tugas tindak lanjut, bukan nomor dummy. Besaran iuran dan kewajiban ditentukan konfigurasi sah HR-02, bukan diasumsikan dari nomor peserta.

**EMP-03 — Bank dan rekening penggajian:** master bank dengan kode/nama bank, nomor rekening sebagai string, nama pemilik sesuai bank, cabang bank bila diperlukan, jenis rekening, currency, rekening utama, tanggal efektif, status verifikasi dan lampiran. Dukung histori rekening; hanya satu rekening utama aktif per skema pembayaran pada satu waktu. Rekening pengganti diajukan → diverifikasi HR/finance → berlaku pada payroll yang belum dikunci. Batch pembayaran menyimpan snapshot rekening sehingga perubahan profil setelah approval tidak mengalihkan dana; penggantian pada batch memerlukan approval ulang. Rekening bukan milik karyawan atau rekening bersama ditandai untuk pemeriksaan khusus, bukan diterima tanpa verifikasi. Metode tunai jika diizinkan memakai tanda terima, bukan rekening palsu.

**EMP-04 — Hubungan kerja dan dokumen:** tanggal bergabung, status proses onboarding/aktif/cuti panjang/nonaktif/keluar, jenis hubungan kerja, nomor/versi kontrak, tanggal mulai/berakhir, masa percobaan jika berlaku, cabang, departemen, jabatan, grade, atasan, cost center, jadwal dan **skema payroll beserta frekuensi gaji mingguan/bulanan yang menjadi bagian profil karyawan** (`EMP-01A`, `HR-03A`). Simpan gaji/komponen bertanggal dengan akses terbatas, histori kontrak/perpanjangan, mutasi, promosi, pelatihan, apresiasi/peringatan sesuai kebijakan, surat penugasan dan dokumen keluar. Reminder kontrak/sertifikasi mendekati habis tidak otomatis memutus hubungan kerja. Checklist keluar mencakup pinjaman, uang muka, aset/tools, hak payroll dan penghentian akun; histori tidak dihapus saat karyawan keluar.

**EMP-05 — Validasi, self-service dan histori:** tanggal lahir harus tanggal valid dan tidak di masa depan; NIK/identitas aktif duplikat diblokir untuk pemeriksaan, bukan menghasilkan orang kedua. Validasi format tidak membuktikan identitas/BPJS/rekening benar: catat siapa yang memverifikasi dan sumber buktinya. HR dapat menyimpan onboarding draft yang belum lengkap dengan checklist; aktivasi payroll membutuhkan identitas, syarat kerja dan metode pembayaran tervalidasi, sedangkan status BPJS/pajak yang belum selesai ditangani exception sesuai ketentuan sah. Permintaan koreksi profil, unggah dokumen, cuti, pinjaman, lembur dan unduh slip tersedia di self-service sesuai izin. Data identitas/medis tidak ikut ekspor direktori umum; akses penuh dan ekspor sensitif diaudit.

**EMP-06 — Pelepasan karyawan dan hak akhir:** proses keluar dimulai dari pengajuan/notifikasi dengan tanggal pengunduran diri atau akhir kontrak dan **tanggal efektif keluar** yang jelas. Karyawan tetap dapat mengajukan cuti, lembur, dan koreksi absensi selama masih aktif; pengajuan sesudah tanggal efektif ditolak atau diselesaikan sebagai penyelesaian akhir, bukan transaksi normal. Perhitungan akhir memuat: gaji prorata sampai tanggal efektif pada frekuensi pekerja (`EMP-01A`, `HR-03A`), lembur yang sudah disahkan dan belum terbayar (`HR-09A`), sisa cuti yang dibayar/ hangus sesuai kebijakan, potongan pinjaman/uang muka dengan opsi pelunasan atau sisa kewajiban, dan komponen sesuai kebijakan (mis. THR/pesangon **sesuai aturan yang disahkan HR/finance, bukan angka yang ditanam di kode**). Settlement akhir dijalankan sebagai run penyelesaian bertanggal; take-home tidak boleh negatif otomatis — kekurangan menjadi piutang karyawan dengan jadwal pelunasan atau write-off berizin (`LN-04`). Lembur/penugasan yang belum disetujui sebelum keluar tidak otomatis dibayar, tetapi tetap ditinjau dengan bukti. Slip, hak, dan histori tetap dapat diakses dan tidak dihapus; akun aplikasi dinonaktifkan tanpa menghapus pegawai, dan bukti pembayaran akhir tersimpan.

**ORG-01 — Master departemen:** departemen memiliki kode/nama, cabang, **induk departemen (parent) opsional untuk sub-bagian** (mis. Produksi → Fabrikasi/Body Repair/Painting; Gudang → Rak/Area), kepala departemen, cost center (dan profit center bila berlaku), status aktif serta tanggal berlaku. Hierarki tidak boleh membentuk siklus; departemen dapat dikaitkan ke lebih dari satu cabang bila memang berlaku, tetapi penempatan karyawan tetap menunjuk satu departemen efektif. Kepala departemen boleh memiliki **pelaksana tugas (PLT)/pengganti berbatas waktu** agar approval operasional (termasuk lembur `HR-07`) tetap berjalan saat kepala tetap tidak tersedia; PLT tercatat dengan rentang tanggal dan wewenang yang diberikan, bukan asumsi diam-diam. Cost/profit center bertanggal berlaku dan dipakai penempatan serta costing (`ORG-02`, `MOD-09`). Departemen yang sudah dipakai tidak dihapus; hanya dinonaktifkan dan digabung lewat aturan merge/alias yang disahkan.

**ORG-01A — Master jabatan, grade dan struktur karier:** jabatan memiliki kode/nama, uraian tugas, kompetensi wajib, status aktif, dan **relasi ke departemen**: dimiliki satu departemen, atau ditandai **lintas-departemen** bila memang generik (mis. Mekanik, Teknisi Gudang). Grade/level mengatur **jenjang** (mis. Junior/Madya/Utama) dan kebijakan benefit/rentang sesuai izin, terpisah dari role aplikasi. Sistem mendukung jalur promosi/mutasi antar-jabatan bertanggal dan aturan **duplikasi/alias**: jabatan dengan makna sama dicegah atau digabung lewat aturan yang disahkan, bukan dibiarkan hidup berdampingan tanpa kontrol. Jabatan bukan role RBAC: promosi kepala bengkel tidak otomatis memberi hak `super_admin` atau akses seluruh payroll. Jabatan yang telah digunakan hanya dinonaktifkan, tidak dihapus, agar histori penempatan/payroll tidak putus.

**ORG-01B — Penautan jabatan dan grade ke kebijakan:** grade/jabatan dipetakan ke kebijakan yang berhubungan dengan biaya, dengan **tanggal berlaku** dan pengesahan HR/finance: rentang gaji/upah, kebijakan benefit/tunjangan, serta pemetaan ke kebijakan tarif lembur/costing (dasar upah tetap diambil dari gaji pokok bertanggal `EMP-01A`/`HR-08A`, bukan ditanam di jabatan). Departemen dapat memiliki **batas formasi/headcount**; promosi/mutasi/rekrutmen yang melampaui batas ditolak atau memerlukan approval berizin, bukan lolos diam-diam. Mengubah pemetaan grade/kebijakan **tidak menulis ulang** payroll atau costing posted; kebijakan baru berlaku mulai tanggal efektifnya dan komponen lama tetap dapat direproduksi. Angka rentang gaji dan tarif adalah keputusan HR/finance, dokumen ini hanya menetapkan strukturnya.

**ORG-02 — Riwayat penempatan dan approval:** mutasi/promosi mencatat posisi/cabang/departemen/atasan lama dan baru, tanggal efektif, alasan, surat dan approval. Dukung penugasan sementara dengan batas waktu; cegah penempatan utama yang tumpang tindih dan distribusi biaya melebihi total yang dialokasikan. Dokumen pengajuan menyimpan jalur approver saat diajukan; pergantian atasan memakai reassignment/delegasi tercatat, bukan diam-diam menyetujui ulang. Jadwal, budget, scope akses dan costing mengikuti kebijakan penempatan efektif tanpa mengubah timesheet/payroll posted. Master yang telah digunakan hanya dinonaktifkan, bukan menghapus histori.

### 15.2 Pengajuan cuti, izin dan saldo hak

**LV-01 — Jenis dan kebijakan cuti:** master cuti tahunan, sakit, izin khusus, cuti tanpa upah dan jenis lain sesuai ketentuan yang disahkan; kode/nama, paid/unpaid, memakai kuota atau tidak, kelayakan masa kerja, periode hak, accrual/pemberian hak, prorata, carry-over/expiry, durasi minimum, tenggat pengajuan dan kebutuhan lampiran. Aturan jenis cuti tidak disamakan: sakit/izin khusus tidak otomatis mengurangi hak cuti tahunan. Nilai hak dan syarat dokumen ditetapkan HR sesuai aturan berlaku, bukan angka tetap universal.

**LV-02 — Alur pengajuan:** karyawan/self-service atau HR atas nama karyawan membuat draft berisi jenis, tanggal/jam mulai-selesai, durasi, alasan, lampiran privat, pengganti/handover dan kontak bila relevan → submit → pemeriksaan atasan/ketersediaan tim → verifikasi HR menurut matriks → approved/rejected. Simpan pemohon asli dan petugas yang menginput. Kalender tim menampilkan ketidakhadiran seperlunya, bukan alasan medis. Perubahan tanggal/jenis/durasi setelah submit membatalkan approval lama dan perlu pengajuan ulang; pembatalan approved memerlukan persetujuan pembatalan.

**LV-03 — Perhitungan hak dan kontrol:** ledger mencatat hak diberikan/accrued, saldo awal, carry-over, expiry, penyesuaian approved, pemakaian dan pembatalan. Durasi cuti berdasarkan roster efektif/kalender serta interval kerja, bukan sekadar selisih tanggal; hari istirahat/libur tidak memotong cuti kerja kecuali ketentuan jenisnya memang memakai hari kalender. Dukung setengah hari/jam menurut kebijakan. Permintaan submitted mereservasi kuota yang relevan; approval memindahkan reservasi menjadi pemakaian tanpa pemotongan kedua kali; reject/withdraw mengembalikan reservasi, pembatalan approved membalik pemakaian satu kali. Saldo tersedia = hak neto − pemakaian approved − reservasi pending. Lock saldo mencegah dua pengajuan bersamaan memakai hak yang sama; saldo negatif dan overlap pengajuan ditolak kecuali jenis/kebijakan eksplisit mengizinkannya.

**LV-04 — Dampak operasional dan payroll:** cuti approved memperbarui ketersediaan roster/kapasitas, kalender tim dan absensi; konflik dengan penugasan/shift diselesaikan sebelum pekerjaan dirilis. Cuti tanpa upah memengaruhi payroll dengan dasar potongan yang disahkan; cuti berbayar tidak otomatis menjadi absensi tanpa keterangan. Tanggal lintas tahun memakai bucket hak yang sesuai, tidak mengambil seluruhnya dari satu tahun secara diam-diam. Koreksi setelah payroll posted memakai adjustment terkait; sakit darurat dapat dicatat retrospektif dengan verifikasi, bukan menimpa payroll lama. Contoh kuota: hak 12 hari, approved 2 hari, pending 1 hari → tersedia 9 hari; pending disetujui → tetap 9 hari; pembatalan approved 1 hari → 10 hari. Ini contoh hitung, bukan penetapan hak hukum semua pekerja.

### 15.3 Pengajuan pinjaman karyawan dan cicilan

**LN-01 — Jenis dan batas:** pinjaman pribadi karyawan/kasbon gaji dibedakan dari uang muka operasional PC-02 dan reimbursement PC-04. Master jenis pinjaman menetapkan eligibility, limit nominal/saldo berjalan, tenor, awal cicilan, metode pengembalian, batas potongan, persyaratan dan matriks approval. Default rancangan pinjaman karyawan tanpa bunga; bunga/biaya hanya boleh diaktifkan jika ada kebijakan dan perjanjian sah, ditampilkan terpisah dari pokok. Banyak pinjaman per orang dimungkinkan dengan pemeriksaan gabungan saldo serta potongan, bukan limit per dokumen saja.

**LN-02 — Pengajuan sampai pencairan:** draft oleh karyawan/HR atas nama karyawan → submitted → review HR atas status kerja/saldo/potongan → approval atasan/owner/finance menurut nominal → perjanjian dan persetujuan potongan → approved → pencairan posted → active → paid-off/closed. Field: pemohon, tujuan, jumlah diminta/disetujui, tanggal, tenor, rencana cicilan, rekening penerima terverifikasi, lampiran dan persetujuan. Penolakan/pembatalan sebelum pencairan tidak membentuk piutang. Approval saja tidak dianggap dana diterima; bukti dan nominal pencairan tercatat, termasuk pencairan parsial. Jadwal aktual mengikuti pokok yang benar-benar dicairkan dan amendemen yang disetujui, tidak memotong jumlah yang belum diberikan.

**LN-03 — Ledger, cicilan dan payroll:** ledger per pinjaman memisahkan pokok dicairkan, pembayaran manual, potongan payroll posted, reversal, biaya/bunga jika berlaku dan saldo. Total cicilan pokok sama dengan pokok terutang; residual pembulatan ke cicilan terakhir. Payroll draft hanya merencanakan potongan, tidak mengurangi piutang; posting payroll membukukan potongan yang sah sekali dan menyimpan link cicilan. Pembayaran manual sebelum posting payroll harus mengurangi rencana potongan secara atomik; jangan menagih cicilan yang sudah dilunasi. Limit potongan mempertimbangkan seluruh kewajiban pekerja dan ketentuan/perjanjian yang sah. Jika gaji tidak mencukupi, jangan otomatis membuat take-home pay negatif: catat sisa jatuh tempo/tunggakan dan minta penyelesaian atau reschedule approved.

**LN-04 — Pelunasan dan pengecualian:** dukung pelunasan dipercepat, pembayaran sebagian, tunggakan, penundaan/reschedule, pembatalan sisa pencairan dan write-off dengan alasan/approval. Perubahan jadwal tidak menghapus cicilan dan pembayaran lama. Reversal payroll mengembalikan potongan/piutang satu kali sesuai referensi asal. Saat karyawan resign/kontrak berakhir, saldo tetap terbuka sampai ada settlement sah; potongan final payroll tidak boleh otomatis menghabiskan seluruh hak tanpa dasar/otorisasi. Notifikasi menyatakan nominal jatuh tempo tanpa menyebarkan alasan pinjaman ke pihak tidak berizin.

**LN-05 — Jurnal, contoh dan laporan:** pencairan Dr piutang pinjaman karyawan / Cr bank/kas; pengembalian tunai Dr bank/kas / Cr piutang pinjaman; potongan payroll Dr utang gaji / Cr piutang pinjaman (atau bagian ekuivalen jurnal payroll yang sama, tidak keduanya). Pemberian pinjaman bukan beban gaji dan pengembalian pokok bukan pendapatan. Contoh tanpa bunga: pencairan Rp3.000.000, tenor 6 kali → Rp500.000/cicilan; dua cicilan posted → saldo Rp2.000.000; satu cicilan tersebut direverse → saldo Rp2.500.000. Laporan menampilkan pengajuan diminta/disetujui/dicairkan, jadwal, piutang per orang, potongan payroll, pembayaran manual, aging tunggakan, reschedule dan rekonsiliasi akun kontrol piutang ke GL.

### 15.4 Aset dan maintenance

**AST-01:** aset tetap, kategori, metode/masa manfaat/nilai residu, lokasi/custodian, tanggal siap digunakan, depresiasi, transfer, revaluasi jika kebijakan mengizinkan, impairment/disposal dan jurnalnya.

**AST-02:** preventive/corrective maintenance mesin, jadwal kalibrasi alat ukur, work request, downtime, spare part dan biaya. Depresiasi mesin produksi dapat menjadi overhead; mobil owner/pribadi tidak otomatis menjadi aset usaha.

**AST-02A — Kalibrasi sebagai gate mutu dan keselamatan:** status kalibrasi alat ukur berversi bertanggal (tanggal kalibrasi terakhir, jatuh tempo berikutnya, sertifikat/bukti, laboratorium/kalibrator, hasil lulus/tidak). Alat ukur yang **kedaluwarsa** atau dinyatakan tidak lulus tidak dapat dipakai pada tahap yang memerlukan pengukuran sesuai kebijakan mutu; bila tetap dipakai, sistem wajib memblokir atau menandai exception dengan approval berizin dan alasan, bukan sekadar peringatan yang diabaikan. Ukuran yang dihasilkan alat tidak valid setelah jatuh tempo ditandai agar pengukuran/tahap terpengaruh ditinjau ulang. Penggunaan alat ukur untuk pengukuran kritis harus menunjuk alat yang kalibrasinya masih berlaku; izin memakai/menandai alat dipisah dari izin mencatat hasil QC. Ini adalah keputusan **mutu/keselamatan/teknis** yang disahkan bersama engineering/QC, bukan preferensi UI.

**AST-03 — Revaluasi, impairment, dan disposal aset:** selain penyusutan berjalan, nilai aset dapat berubah karena peristiwa yang memerlukan dokumen tersendiri, bukan sekadar mengedit angka di register.

**Revaluasi (bila kebijakan mengizinkan, `AST-01`):** hanya dengan kebijakan yang disahkan, jadwal berkala, dasar penilaian (appraiser/jasa penilai atau indeks) dan bukti; mencatat nilai sebelum, nilai setelah, selisih, akun tujuan (surplus revaluasi vs laba rugi) sesuai kebijakan akuntansi yang disahkan finance, serta tanggal efektif. Revaluasi tidak boleh dipakai menutupi penyusutan yang seharusnya berjalan atau mengubah masa manfaat diam-diam.

**Impairment/penurunan nilai:** ketika aset rusak berat, tidak terpakai, atau nilainya turun permanen, penurunan nilai memerlukan justifikasi, bukti kondisi (foto/diagnosa bengkel), perhitungan nilai yang dapat dipulihkan, approval berjenjang, dan jurnal penurunan; setelah impairment, penyusutan mengikuti basis baru sampai ada pemulihan yang juga berdokumen. Aset yang berhenti dipakai diberi status dan alasan (`idle`, `rusak`, `menunggu disposal`) yang terlihat di register (`REP-19`), bukan dibiarkan terdaftar aktif.

**Disposal/penghapusan (jual, tukar tambah, scrap, hibah, musnah):** memuat alasan, tanggal efektif, nilai buku saat keluar, harga jual/penerimaan bila ada, biaya keluar, laba/rugi disposal, dan approval; aset yang dijual/discrap tidak boleh tetap disusutkan setelah tanggal disposal. Penjualan aset memiliki dokumen penerimaan kas/piutang sendiri dan **tidak boleh dicatat sebagai penjualan barang dagang**; tukar tambah memisahkan nilai aset lama dan nilai perolehan aset baru. Alat ukur berkalibrasi (`AST-02A`) yang masuk disposal berhenti dipakai pada tahap mutu, sama seperti saat kalibrasinya kedaluwarsa.

Seluruh peristiwa di atas menyimpan **riwayat nilai aset bertanggal** (perolehan → revaluasi → impairment → disposal) agar perubahan nilai dapat direkonsiliasi dengan jurnal dan laporan aset, bukan menimpa histori dengan angka baru. Batas kewenangan (siapa boleh menilai ulang, men-impair, dan menghapus aset) adalah **keputusan yang perlu disahkan owner/finance**, bukan asumsi bawaan sistem.

## 16. Dokumen, status, pembatalan, dan audit

**CTL-01:** pola umum draft → submitted → approved → posted → reversed, dengan rejected/cancelled sebelum posting. Tidak semua dokumen memakai seluruh status: PO memiliki ordered/partial/closed; GR inspection/accepted; WO released/in-progress/QC/completed. Matriks transisi per dokumen ditetapkan sebelum implementasi modul; transisi ilegal ditolak server.

**CTL-02:** status approval, fulfillment, pembayaran, matching dan financial posting adalah sumbu terpisah. Paid tidak berarti received; completed marketplace tidak berarti matched; WO completed tidak otomatis invoice paid.

**CTL-03:** draft dapat diedit sesuai izin. Dokumen posted immutable; koreksi melalui reversal, credit/debit note atau adjustment yang menyimpan referensi asal. Pembatalan dokumen induk memeriksa downstream stock, invoice, payment dan periode; tidak menghapus cascade transaksi historis.

**CTL-04:** nomor dokumen unik berdasarkan jenis/cabang/periode dan sequence terkunci; tidak `count()+1`. Nomor dokumen batal tidak digunakan ulang. Referensi eksternal marketplace unik dalam scope platform/akun/toko yang sesuai. Nomor dokumen **selalu terisi otomatis** dan tidak pernah diketik pengguna; nomor barang/kode master mengikuti aturan yang sama (selalu terisi, berurutan, tidak dipakai ulang). Rincian aturan ada di `docs/prd.md` §12 poin 8–10. Tampilan nilai uang memakai Rupiah bergaya Indonesia (`Rp1.250.000,00`) dan tanggal memakai nama bulan Indonesia berurutan tanggal–bulan–tahun (`4 Oktober 2026`); penyimpanan tetap `Decimal(15,2)` dan `YYYY-MM-DD`, sesuai `CST-09` dan `TECH-09`.

**CTL-05:** idempotency key untuk posting, pembayaran, konversi penawaran dan impor/webhook; key dengan payload berbeda ditolak. Unique constraint per sumber/peristiwa posting mencegah duplicate walau request berbeda.

**CTL-06:** audit mencatat siapa, kapan, perubahan sebelum/sesudah, alasan, approval dan correlation ID. Lampiran invoice/foto/desain berversi dengan hak akses; tidak menyimpan secret/password di audit. Audit transaksi tidak dapat dihapus oleh pengguna operasional.

## 17. Arsitektur target Laravel dan integrasi

### 17.1 Keputusan teknis dasar

**TECH-01:** baseline backend Laravel 13.x dengan patch stabil terbaru yang masih didukung saat implementasi, PHP kompatibel (rentang dukungan Laravel 13: 8.3–8.5), **MySQL 8.x dengan mesin InnoDB**. Versi mayor dan rentang PHP mengacu [release notes Laravel](https://laravel.com/docs/releases); patch/runtime final dikunci setelah verifikasi dependency. Arsitektur modular monolith untuk menjaga transaksi lintas stok/jurnal/WIP; bukan microservices untuk ledger inti.

**TECH-01A — keputusan owner: MySQL 8.x, bukan MariaDB dan bukan SQLite.** Produksi, pengembangan, dan pengujian memakai **MySQL 8.x yang sama**. Yang dimaksud bukan "kompatibel dengan MySQL", melainkan benar-benar dijalankan di MySQL 8.x.

Alasan pemisahan ini penting: sistem ini bersandar pada transaksi lintas stok dan jurnal, kunci unik untuk idempotensi jurnal, dan kolom `DECIMAL` untuk uang. Perbedaan kecil antar basis data pada perilaku unik, penyortiran, tipe kolom, dan semantik transaksi dapat membuat aplikasi berjalan mulus di pengembangan tetapi gagal atau — lebih buruk — memberi hasil berbeda di produksi. Karena itu pengembangan dan test **wajib** memakai mesin yang sama dengan produksi, bukan basis data yang lebih ringan.

Konsekuensi yang diterima: setiap lingkungan kerja menuntut server MySQL 8.x yang berjalan, dan pengujian menjadi sedikit lebih lambat dibanding basis data dalam memori. Batas ini diterima sadar karena menyamakan mesin lebih berharga daripada kecepatan menjalankan test.

Kolom uang wajib `DECIMAL`, bukan `FLOAT`/`DOUBLE`. Data turunan dan append-only seperti jurnal tetap mengandalkan penguncian baris dan transaksi InnoDB sebagaimana dirancang pada `TECH-03`.

**TECH-02:** target web wajib SPA React + TypeScript strict + Vite + Tailwind CSS + shadcn/ui keluarga Base UI, memakai `cmdk` asli untuk Command Palette, searchable Combobox, TanStack Query/Table, React Hook Form dan Zod. Responsif untuk desktop/tablet/HP dan mengonsumsi JSON API Laravel `/api/v1`; bukan frontend Blade/Livewire atau Vue paralel. Versi baseline dan kebijakan pembaruan terdapat pada §17.6. Web dan Android memakai kontrak serta application Action/domain Service yang sama. Validasi klien membantu pengguna, tetapi izin, approval, DP, saldo, costing dan posting tetap diputuskan server. Spesifikasi visual, daftar komponen wajib dan quick add dirinci pada [spesifikasi web](spesifikasi-web-quick-add.md).

**TECH-03:** Controller/Form Request → application Action → domain Service → persistence. Posting stok, costing dan jurnal dipanggil eksplisit dalam satu transaksi database; tidak bergantung Observer Eloquent tersembunyi. Service yang menerima transaksi tidak melakukan commit parsial sendiri.

**TECH-16 — CRUD wajib di seluruh modul, dengan aksi terkontrol untuk data turunan:** setiap MOD-01–14 wajib menyediakan pengelolaan data yang **dimilikinya** secara penuh — create, read, update, nonaktifkan/hapus, dan (bila relevan) approve/post/reverse — lewat API dan UI, tanpa menuntut vendor. Penyelesaian berlaku umum: **penghapusan pada data yang punya histori tidak menghapus baris, melainkan menonaktifkan** (soft delete/`deactivate`), sedangkan dokumen yang sudah diposting tidak diedit dan dikoreksi lewat reversal/credit-debit note.

Data **turunan** tidak boleh disunting langsung, karena mengeditnya berarti menghapus jejak dan membuat laporan tidak dapat direkonsiliasi. Kategori ini mencakup **jurnal dan baris jurnal** (lahir dari posting, bukan ketikan), **saldo stok, stock move, layer FIFO dan konsumsinya**, **open item, GRNI, akrual**, **entri biaya job, komitmen, variance overhead**, **ringkasan absensi**, **payslip, ledger pinjaman, ledger/saldo cuti**, **register aset dan entri penyusutan**, **audit event**, **approval task**, dan **token/tautan publik**. Data turunan tetap dapat diubah, tetapi hanya melalui **aksi terkontrol yang eksplisit, berizin, beralasan, dan berjejak** — misalnya membatalkan jurnal lewat `void` dengan alasan dan approval, menyesuaikan stok lewat `stock-count`/opname, menyelesaikan approval lewat keputusan (bukan menghapus task), menyetujui/mencabut akses portal lewat `grant/revoke`, dan menerima/menolak penawaran publik lewat aksi token. Tidak boleh ada endpoint generik `POST`/`PATCH`/`DELETE` bebas pada tabel ledger, saldo, maupun audit.

Izin mengikuti peran dan pemisahan tugas (`SEC-01..04`), bukan sekadar kepemilikan tombol: pengguna yang boleh membuat master tidak otomatis boleh memposting jurnal atau menghapus aset. Setiap perubahan pada data turunan menyimpan aktor, waktu, alasan, dan sumber, agar laporan dapat direkonsiliasi ulang (`RPT-01`).

**TECH-04:** service terpisah untuk FIFO, landed cost, cost adjustment/genealogi, journal posting, WIP/job costing, period lock, document sequence, approval, tax, UoM, payroll dan reconciliation. Hindari dua implementasi rumus yang berbeda antara preview UI dan posting.

**TECH-05:** queue untuk ekspor, notifikasi dan integrasi setelah commit; kegagalan notifikasi tidak membatalkan transaksi bisnis yang sudah sah. Outbox/idempotensi untuk pengiriman ulang; stok/jurnal inti tidak ditunda ke queue tanpa jaminan atomisitas yang setara.

**TECH-06:** autentikasi sesi untuk web, MFA bagi akun sensitif, Laravel Policies/Gates dan permission registry tunggal untuk enforcement. Bila memigrasi izin lama, mapping string eksplisit tanpa alias yang membingungkan; navigasi UI turunan izin, bukan sistem izin kedua yang dapat drift.

### 17.3 Integrasi

**INT-01 — Wajib:** impor master, saldo awal, listing/order marketplace dan rekening koran melalui template dengan preview, validasi, report error, deduplikasi dan audit; ekspor laporan; scanner barcode/QR; lampiran; notifikasi in-app dan email.

**INT-02 — Kontrak API untuk seluruh modul:** setiap fungsi bisnis wajib MOD-01–14 tersedia melalui API `/api/v1`, termasuk transisi approval/posting/reversal, lampiran, laporan dan ekspor; bukan hanya CRUD master. Kontrak target ada di [kontrak API ERP v1](kontrak-api-erp-v1.md). Web dan Android tidak memiliki implementasi ledger/aturan bisnis yang berbeda. Penyediaan API tidak otomatis berarti aplikasi Android telah dibuat atau integrasi provider INT-03 telah tersedia.

**INT-03 — Bersyarat:** sinkron marketplace, bank feed, WhatsApp, e-invoice/pajak dan mesin absensi hanya dapat dinyatakan selesai setelah provider, izin, biaya, spesifikasi API dan sandbox tersedia. Tidak menjanjikan scraping atau akses order marketplace tanpa hak. Jalur manual/impor tetap operasional dan bukan data simulasi.

**INT-04 — Portal pelanggan:** akses hanya data sendiri, quotation/change approval, status/foto yang dipublikasikan, invoice, pembayaran yang terverifikasi dan tiket garansi. Token tautan memiliki expiry; nominal diterima tidak dipercaya dari callback klien tanpa verifikasi server.

**INT-04A — Tautan publik penawaran dan e-sign:** penawaran yang berstatus dikirim dapat menghasilkan **tautan publik bertoken** (bukan tautan internal yang bisa ditebak) untuk dibuka pelanggan tanpa akun. Halaman tautan menampilkan **penawaran versi terkunci** (bukan cost/margin internal), syarat, masa berlaku, dan tombol terima/tolak. Data tautan: `grant_id`, referensi quotation+version, scope customer/contact, **masa berlaku token**, status single-use atau multi-view, dan riwayat akses. **Masa berlaku tautan publik ditetapkan 14 hari kerja** (hari kerja menurut kalender kerja bengkel; hari libur tidak dihitung). Penghitungan hari kerja ini konsisten untuk tautan penawaran (`INT-04A`) dan tautan pemantauan progres (`INT-04C`). Token yang kedaluwarsa/dicabut/dipakai menerima halaman aman, bukan penawaran kosong yang bisa dikira masih sah. Perpanjangan masa berlaku dapat dilakukan dengan **menerbitkan token baru berreferensi versi yang sama**, bukan memperpanjang token lama secara senyap.

**E-sign penawaran:** penerimaan penawaran dilakukan lewat **tanda tangan digital** yang mengikuti kebijakan tanda tangan yang sama dengan inspeksi kendaraan (`VEH-02A`) — setara tanda tangan basah, terikat pada identitas penanda tangan, waktu, versi dokumen, dan bukti, dengan jejak `signed_by`, `signed_at`, `document_version`, `evidence_id`. Persetujuan mencatat nama penerima, peran (pelanggan/perwakilan), waktu, alamat/IP bila diambil, dan versi penawaran yang disetujui; versi yang di-supersede tidak dapat disetujui. **Acceptance pelanggan tidak menggantikan approval internal** dan tidak dengan sendirinya merilis pekerjaan: setelah accepted, sistem masih menuntut pemenuhan gate DP (`SAL-09`) sebelum WO dirilis.

**INT-04B — Instruksi pembayaran (rekening dan nominal):** setelah penawaran diterima, tautan/portal menampilkan blok **instruksi pembayaran** berisi nominal yang harus dibayar (misalnya DP minimum 50% dari grand total yang tercantum), rincian dasar hitung, dan **rekening pembayaran resmi** (bank, nomor rekening, nama pemilik, kode/QRIS/VA bila ada, sesuai master metode pembayaran `MD-08A`). **Rekening ditampilkan penuh** (nomor rekening lengkap terlihat) agar pelanggan dapat langsung menyalin dan membayar; nomor disimpan sebagai string dan hanya datang dari master resmi. Rekening yang ditampilkan adalah **rekening resmi bertanggal dari master**, bukan rekening yang diketik ulang; perubahan rekening **tidak boleh** dikirim hanya lewat pesan/telepon tanpa verifikasi, dan tautan harus memberi penanda anti-fraud (misalnya peringatan "hanya percaya rekening pada tautan resmi ini"). Nominal ditampilkan dari perhitungan server atas dokumen (grand total, DP, sisa), bukan angka yang bisa diubah klien. Pelanggan dapat mengunggah **bukti transfer**; bukti itu berstatus **verifikasi pending** sampai diverifikasi finance (`SAL-10`, `FIN-15`), **bukan** pembayaran sah atau pembuka gate DP. Pemantauan status pembayaran hanya menampilkan penerimaan yang sudah `terverifikasi/posted` (`INT-04`).

**INT-04C — Pemantauan progres pengerjaan kendaraan:** pelanggan pemegang tautan/akses portal dapat memantau pekerjaan mobilnya secara langsung: **status tahap** job/WO (`FAB-01`, `FAB-05`), progres per tahap, **foto/dokumen yang dipublikasikan** (check-in, in-progress, QC akhir — bukan foto internal sembarang), tanggal mulai dan estimasi/aktual selesai, daftar pekerjaan yang disetujui, perubahan yang menunggu persetujuan (`change order`), status QC dan checklist akhir (`FAB-13`), status serah terima, serta tagihan dan status pembayarannya. Hanya data **published** milik pelanggan itu yang tampil; **biaya internal, margin, harga pokok, gaji, dan data pelanggan lain tidak pernah bocor**. **Foto yang dipublikasikan disaring sebelum tayang**: foto internal yang memuat wajah mekanik, unit/kendaraan pelanggan lain, dokumen berisi harga/margin, atau papan tulis internal tidak boleh ikut terbit; penyaringan dapat berupa pengaburan otomatis dan/atau persetujuan manual kepala bengkel sebelum publikasi, dan setiap publikasi tercatat bersama siapa yang menyetujui. Publikasi foto/status berada di bawah kendali berizin (kepala bengkel/admin). Jika tautan digunakan pihak lain, akses tetap dibatasi pada data pelanggan pemilik grant, bukan hanya "siapa pun yang memegang URL".

### 17.4 API-first dan kesiapan Android

**TECH-07 — Kontrak dan cakupan:** katalog resource/aksi pada kontrak API memetakan MOD-01–14 dan REP-01–21. Implementasi wajib menyediakan OpenAPI 3.1 dengan request/response/error schema, contoh, security scheme, permission dan transisi tiap operasi; spesifikasi Markdown saat ini bukan klaim bahwa file OpenAPI atau endpoint sudah diimplementasikan. Semua requirement wajib dipetakan ke operation ID dan bukti penerimaan; endpoint placeholder, respons dummy, atau CRUD tanpa aksi domain tidak memenuhi cakupan.

**TECH-08 — Identitas klien dan keamanan:** web memakai sesi cookie Laravel Sanctum dengan CSRF; Android memakai bearer token per perangkat, memiliki expiry dan dapat dicabut. MFA akun sensitif, pembatasan login, logout perangkat, revoke seluruh perangkat dan pembatasan field/cabang berlaku server-side. Token tidak disimpan plaintext di log; Android memakai penyimpanan terlindungi platform, web tidak menyimpan bearer token di localStorage. Token perangkat tidak menggantikan permission terbaru atau approval.

- **Produsen potret kesehatan sistem**, POTONGAN 134. Halaman Kesehatan Sistem (Potongan 132) berlayar tetapi selalu "Tidak diketahui": API-23 HANYA membaca tabel `system_health_snapshots`, dan **tidak ada apa pun di aplikasi yang menulisnya** — layar lengkap tanpa produsen potret sama saja tidak berfungsi. - **Cadangan nyata dan dapat diunduh**, POTONGAN 135. Kartu "Cadangan" pada Kesehatan Sistem menampilkan angka dummy karena tidak ada satu pun berkas cadangan sungguhan — hanya nilai contoh. Unduhan ada di `BackupController` (`GET /backups`, `GET /backups/{berkas}`) dengan izin tersendiri `backups.read`/`backups.download` (melihat status ≠ mengunduh seluruh database), nama berkas divalidasi regex ketat sehingga `../..%2F.env` dan nama tak dikenal dijawab `404`, dan unduhan dialirkan (`streamDownload`) sehingga `bagiPath()` versi rekaman dikecualikan untuk path `backups` — tanpa itu aliran berkas besar memicu `500`. - **Keputusan kredit dan penyuntingan dari data server**, POTONGAN 136. Dua keluhan nyata dari pemakaian. Pertama, `credit_status` pelanggan **selalu** `belum_disetujui`: field-nya `createOnly` di form, dan tidak ada endpoint yang menyetujuinya — jadi setiap pelanggan mustahil diberi kredit. Kedua, saat "Ubah" data tidak ditarik ulang dari server: form diisi dari salinan BARIS DAFTAR, bukan `GET /{resource}/{id}`. Pabrik hook master diperluas dengan `useDetail`, dan dialog ubah kini **dibaca ulang dari server lebih dahulu** (dengan keadaan "Memuat…") lalu dipasang ulang per id — supaya yang disunting adalah nilai yang benar-benar berlaku, bukan salinan yang mungkin sudah basi. Ketiga, temuan lanjutan dari pemakaian: pemilih relasi menampilkan ID mentah ("1") alih-alih nama ("Umum") **dan** pilihan yang sudah diklik kembali kosong. Satu akar masalah: `AsyncCombobox` merender item sebagai objek `{value,label}` sementara `Combobox.Root` menerima `value` berupa ID string, sehingga Base UI tak dapat mencocokkan keduanya. Perbaikan mengikuti pola resmi "Value selection with IDs": item adalah RECORD asli dan `Combobox.createItems(records, { getValue, getLabel })` memetakan record → ID string untuk seleksi, sementara `Combobox.Item value` diberi ID turunan dan render/filter tetap memakai record; `filteredItems` tetap hanya hasil pencarian server. Label pilihan tersimpan yang di luar halaman pertama diambil dari **relasi bersarang** record (`referenceNestedKey`, konvensi `xxx_id` → `xxx`) atau dengan **membaca satu record itu** dari server lalu menyertakannya ke daftar item. Keempat, cacat itu ternyata berlaku untuk **setiap** field relasi, bukan hanya Kategori: relasi bersarang hanya dikirim sebagian server, dan sebagian master tidak punya endpoint detail sama sekali (`customer-payment-terms`, `asset-categories` → 404). Bukti: `CustomerCreditTest` 21/21 dan `MasterDataCrudTest` 14/14 (termasuk termin pelanggan tanpa endpoint detail, ID tak dikenal → daftar kosong, kolom di luar allowlist → `422`); `GET /asset-categories?filter[id]=1` → `[]` (sebelumnya keliru mengembalikan baris 4–5). Penulis berkas: CSV HP murni ber-BOM UTF-8 (dengan netralisasi sel yang dapat dieksekusi spreadsheet — `=`/`+`/`-`/`@`, persis pola §3.2 `compare.md`), XLSX lewat `phpoffice/phpspreadsheet`, PDF lewat `barryvdh/laravel-dompdf` (keduanya disetujui pengguna). Perintah `erp:export-run` menyapu antrean (idempoten terhadap `queued`, plus `--job=ID`) dan dijadwalkan tiap menit; `AsyncJob` dimajukan bersamanya. Hasilnya berkas **privat** di disk `local` (`result_path`/`result_media_type`/`finished_at` lewat migrasi baru), dan keluar **hanya** lewat `GET /export-jobs/{id}/content` berizin tersendiri `export-jobs.download` — streaming, `Content-Disposition: attachment`, `nosniff`, memeriksa kepemilikan perusahaan (perusahaan lain → `404`, bukan `403`) dan kedaluwarsa (24 jam). Daftar sumber disatukan: `ImportExportService` tidak lagi menyimpan salinannya sendiri, melainkan meminjam `ExportService::daftarSumber()` agar permintaan dan produsen tak bisa berbeda pendapat. Bukti: `ExportJobTest` 16/16 (ketiga tanda tangan format nyata, anti-injeksi, izin, kedaluwarsa, perusahaan lain, `has_result`), `AttachmentAndNotificationTest` 33/33. Berkembang dari desain: ekspor TIDAK dipaksa lewat slot `uploads`/pemindaian karena berkasnya lahir dari data kita sendiri, bukan unggahan tak terpercaya.
- **Header keamanan + CSP**, POTONGAN 140. Aplikasi SPA+API satu origin sama sekali tidak memasang header keamanan: tanpa penolakan iframe, tanpa `nosniff`, tanpa CSP. Ditutup dengan middleware global `SecurityHeaders` yang dipasang **paling awal** (header tetap terkirim walau request ditolak) dan kebijakannya ditaruh di `config/security.php`, bukan dipatri di kelas. Header: `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy`, dan `Strict-Transport-Security` (**hanya** di atas HTTPS, tanpa `preload` — itu keputusan operasional). CSP memakai **nonce per-request** (`Vite::useCspNonce()` cara Laravel 13, sehingga `@vite` menempelkannya otomatis; skrip tema inline di shell Blade diberi nonce yang sama) dengan `script-src` **tanpa** `unsafe-inline`, `frame-ancestors 'none'`, `object-src 'none'`. Lingkungan `local` menambah origin Vite + `ws` agar HMR tidak pecah; produksi tidak. Bukti: `SecurityHeadersTest` 8/8 (nonce header = nonce skrip halaman; HSTS absen di http, ada di https; middleware terdaftar global; dapat dimatikan lewat konfigurasi).
- **Paritas izin + de-duplikasi registry**, POTONGAN 141. Kode izin tersebar di tiga tempat (registry, `routes/api.php`, `hasPermission` di frontend) yang mudah menyimpang tanpa terdeteksi — salah ketik seperti `export-job.read` (kurang 's') menghasilkan endpoint yang tak pernah bisa dipanggil siapa pun, diam-diam. Ditutup dengan `PermissionParityTest` yang menjaga dua arah (setiap `permission:…` di route dan setiap `hasPermission(...)` di `resources/js` harus ada di `PermissionRegistry`) plus test anti-duplikat. Test itu langsung menemukan **20 kode izin duplikat**: resource yang sudah ada di `CRUD_RESOURCES` (yang sudah memberi `read`/`create`) lalu dideklarasikan ulang di `EXTRA_PERMISSIONS`. Duplikat dihapus dengan perilaku **identik** — diverifikasi `syncRegistry` melaporkan `created: 0`, sehingga tak ada izin yang benar-benar hilang — dan registry kembali menjadi satu sumber kebenaran: 1082 → 1062 entri, seluruhnya unik. Bukti: `PermissionParityTest` 3/3, `AuthorizationTest` + `ApiErrorEnvelopeTest` 19/19. Yang **jujur dinyatakan belum**: sebagian resource laporan masih memperoleh `create`/`update`/`delete` dari `CRUD_RESOURCES` padahal rutenya hanya `read` — perampingan hak akses (least-privilege) itu pekerjaan lanjutan terpisah yang belum dikerjakan di potongan ini.
- **"Jadikan pesanan" menaut ke pesanan hasilnya**, POTONGAN 142. Keluhan nyata: menekan **Jadikan pesanan** pada penawaran yang diterima memang berhasil, tetapi pengguna ditinggal di halaman penawaran tanpa tahu pesanannya ke mana. Akarnya bukan server — server **sudah** mengembalikan pesanan baru pada respons aksi (`201 { message, data: { id, so_number } }`) — melainkan UI membuang isi respons itu (hanya toast "berhasil" lalu memuat ulang dokumen asal). Ditutup dengan penanda opsional `creates` (`label`/`detailPath`/`numberKey`) pada `DocumentAction`: saat aksi ber-`creates` berhasil, halaman detail menampilkan panel hasil yang menautkan langsung ke dokumen baru, dan toast menyebut nomornya. Aksi `convert` penawaran memakai penanda ini; aksi penghasil dokumen lain dapat memakai kerangka yang sama. Bukti: `QuotationTest` 17/17 (asersi konversi diperkuat agar respons wajib memuat `data.id` + `data.so_number`), verifikasi HTTP langsung (`QT/2026-10/00014` → SO #60 `SO/2026-10/00055`), `tsc`/`oxlint`/`npm run build` bersih.

Bukti seluruh rangkaian ada di `STATUS.md` (Potongan 108–142), termasuk skrip verifikasi HTTP baru (`verify-quotation-docs.sh` 17/17, `verify-calibration.sh` 7/7, `verify-staging-cleanup.sh` 8/8, `verify-vehicle-catalog.sh` 12/12, `verify-uploads.sh` 9/9, `verify-readonly-screens.sh` 11/11, `verify-table-bulk.sh` 10/10, `verify-fintech-notes.sh` 13/13, `verify-hr-payroll-docs.sh` 27/27, `verify-platform-jobs.sh` 10/10, `verify-employee-subresources.sh` 28/28, `verify-nested-subdocs.sh` 11/11, `verify-hr-adjustments.sh` 8/8, `verify-asset-actions.sh` 8/8, `verify-vehicle-handover.sh` 10/10, `verify-vehicle-detail.sh` 10/10, `verify-loan-ledger.sh` 7/7, `verify-readonly-views.sh` 8/8, `verify-page-actions.sh` 12/12, `verify-location-rules.sh` 7/7, `verify-job-publications.sh` 7/7, dan `verify-integrations.sh` 3/3) yang masing-masing lulus tiga kali berturut-turut. **Tidak ada lagi entri hub "Segera" yang belum memiliki layar** (161 entri hub, semuanya berlayar; tab sub-resource karyawan dan halaman detail aset/kendaraan/pekerjaan adalah ANAK dari entri yang sudah ada). Seluruh gap backend-vs-frontend yang pernah dicatat di POTONGAN 125–132 **SUDAH TERTUTUP**, alur quick add `TECH-11..15` **berjalan** (POTONGAN 133), produsen potret Kesehatan Sistem yang hilang **kini ada** (POTONGAN 134), ekspor generik benar-benar menghasilkan berkas (POTONGAN 139), header keamanan + CSP terpasang (POTONGAN 140), dan paritas izin dikunci uji sekaligus registry dibersihkan dari duplikat (POTONGAN 141), serta "Jadikan pesanan" kini menautkan langsung ke pesanan yang baru dibuat (POTONGAN 142). Yang tersisa **bukan** "belum berlayar", melainkan batas yang sengaja tidak dipalsukan (positif palsu audit-final, master kelas S/D yang memang tidak menawarkan popup, koleksi non-paginasi yang berbentuk pandangan, dan komponen `backup` yang diisi pemantau eksternal). ### 18.1 Deployment pada Synology dengan domain melalui Cloudflare

Bagian ini menetapkan **rencana deployment yang dipilih owner**: aplikasi di-host di NAS Synology di bengkel, domain publik diarahkan lewat Cloudflare. Tujuannya agar biaya bulanan tetap dan data operasional tetap di bawah kendali sendiri, tanpa mengorbankan HTTPS, keamanan, dan kemampuan pulih.

| ID | Aspek | Ketetapan |
| --- | --- | --- |
| DEP-01 | Hosting | NAS Synology sebagai host produksi; aplikasi berjalan **di container** (Docker/Container Manager) — bukan paket web station — agar versi PHP, ekstensi, queue worker dan scheduler terkunci sama seperti di pengembangan, bukan bergantung paket yang dipasang manual |
| DEP-02 | Runtime | PHP sesuai rentang `TECH-01` dengan ekstensi wajib (pdo_mysql, mbstring, bcmath, intl, gd/imagick, zip, opcache), fpm, **MySQL 8.x/InnoDB terpisah** (lihat `TECH-01A`), Redis untuk cache/queue/session, Nginx sebagai reverse proxy, `storage` dan `bootstrap/cache` writable |
| DEP-03 | TLS dan domain | Domain di Cloudflare memakai **mode SSL Full (strict)**: Cloudflare ke origin tetap HTTPS dengan sertifikat sah. Mode "Flexible" **dilarang** — selain membuka celah downgrade, kombinasi Flexible dengan pemaksaan HTTPS di Laravel menyebabkan **redirect loop** yang membuat sistem tidak dapat diakses |
| DEP-04 | Asal trafik | **Keputusan owner: origin diakses lewat Cloudflare Tunnel**, sehingga port aplikasi dan database **tidak dibuka ke internet sama sekali** (seluruh trafik masuk lewat tunnel). `TrustProxies` dikonfigurasi agar skema/klien IP benar di balik proxy. Karena tidak ada port yang diekspos, jangan membatalkan pilihan ini dengan "sekadar" membuka port untuk keperluan sementara — justru itu yang membatalkan manfaat terbesarnya |
| DEP-05 | Batas unggah | Batas unggah Cloudflare dan Nginx/PHP diselaraskan untuk lampiran, foto kondisi, dan bukti transfer; unggahan besar memakai alur sebagai berikut: multipart/chunked yang melampaui batas proxy **dipecah di sisi klien** dan digabung di aplikasi, serta disimpan di **private storage** dengan signed URL, bukan disajikan langsung dari folder publik |
| DEP-06 | Queue dan scheduler | Queue worker dijalankan sebagai **proses persisten** (supervisor/container terpisah), bukan `queue:work` sekali jalan atau `sync`; scheduler Laravel dijalankan cron per menit. Ekspor besar, notifikasi dan integrasi bergantung pada dua hal ini (`TECH-05`), dan statusnya terlihat di `/scheduler-status` |
| DEP-07 | Kinerja, kapasitas, dan redundansi NAS | **Keputusan owner: redundansi memakai SHR; kapasitas terpasang 2×4 TB** (usable kira-kira 3,6 TiB setelah paritas). SHR melindungi dari satu kegagalan disk dan penggantian disk berjalan tanpa kehilangan data; volume yang hampir penuh **menurunkan kinerja dan dapat menghentikan pencatatan**, karena itu pemakaian disk dipantau dan sisanya dipertahankan sebagai ruang kepala (minimal 20%). Perlu diperhatikan proporsi pemakaian: **database relatif kecil, sementara lampiran (foto kondisi, bukti transfer, sertifikat, dokumen job) tumbuh cepat dan menjadi penentu utama kapasitas**; retensi lampiran, pemadatan foto, dan batas ukuran berkas ditetapkan agar 4 TB tidak habis sebelum waktunya. SHR melindungi dari kegagalan perangkat, **bukan** dari salah hapus/ransomware/kebakaran — itu tugas backup offsite `DEP-08` |
| DEP-08 | Backup | Backup DB, lampiran **dan konfigurasi** dengan target NFR-06, disimpan **offsite** (di luar NAS) dan **terenkripsi**; snapshot NAS saja tidak dihitung backup karena satu kegagalan perangkat/staf dapat menghapus keduanya. Uji restore berkala menghasilkan bukti, bukan sekadar status tombol |
| DEP-09 | Pemulihan | RTO ≤4 jam diuji nyata, termasuk skenario NAS mati total: aplikasi, DB dan lampiran dapat dipulihkan di perangkat pengganti. **Keputusan owner: UPS tersedia dan koneksi internet memiliki cadangan (failover)**, sehingga mati listrik singkat tidak langsung mematikan sistem dan putusnya satu jalur internet tidak memutus akses. UPS tetap memiliki batas waktu: saat daya habis, NAS harus dimatikan dengan benar, dan durasi itu menentukan berapa lama bengkel masih dapat melayani |
| DEP-10 | Pemeliharaan | **Keputusan owner: tidak ada jam maintenance khusus** — sistem harus tetap melayani kapan pun. Konsekuensi yang harus diterima dan dikelola, bukan diabaikan: deploy dan migrasi dilakukan **tanpa mematikan layanan** (rolling/restart singkat, maintenance mode sesingkat mungkin, migrasi yang kompatibel mundur); **jadwal backup, patch DSM/Synology, dan restart NAS tidak boleh mengganggu jam produksi** sehingga harus ditentukan saat eksekusi; patch keamanan tidak ditunda; deploy memakai `composer.lock`/lockfile (`TECH-13`), bukan `latest`; perubahan berisiko diuji di staging (`DEP-12`) lebih dulu karena tidak ada jendela henti untuk mencoba-coba di produksi |
| DEP-11 | Akses staf lapangan | Karena portal pelanggan (`INT-04A..C`) dan API Android mengarah ke domain publik, trafik luar (foto bukti, e-sign, progres) tetap harus melewati Cloudflare dengan rate limit dan WAF; jangan membuka port admin/sistem lain ke internet demi staf |
| DEP-12 | Lingkungan terpisah | Staging terpisah dari produksi (`NFR-10`); jangan menguji migrasi atau restore pada NAS produksi tanpa jendela pemeliharaan; secret (kredensial DB, API token Cloudflare, kunci enkripsi) disimpan di luar repo |

**Keputusan owner yang sudah ditetapkan (DEP):** (1) **redundansi disk memakai SHR** (Synology Hybrid RAID) sehingga satu kegagalan disk tidak menghilangkan data; (2) origin **diekspos lewat Cloudflare Tunnel**, tanpa membuka port ke internet — konsekuensinya trafik publik tunduk kebijakan dan kuota tunnel, jadi pemantauan pemakaian wajib; (3) **UPS tersedia** dan koneksi internet memiliki cadangan (failover) agar NAS mati listrik tidak memutus sistem secara kasar; (4) **tidak ada jam maintenance khusus** — lihat `DEP-10` untuk konsekuensi yang harus diterima. Ukuran NAS, kapasitas upload yang disepakati, dan penambahan perangkat lain tetap dapat disesuaikan saat sizing. Rencana ini **tidak menyentuh** keputusan akuntansi/pajak; hanya lapisan infrastruktur.

## 19. Migrasi data dan cutover

**MIG-01:** jika memakai sistem lama, inventarisasi tabel, enum/status, satuan, izin, COA dan semantik setiap kolom terlebih dahulu. Jumlah model atau migration tidak boleh dijadikan persentase kesiapan produk.

**MIG-02:** mapping dan dry run mencakup master, saldo awal, layer FIFO beserta qty/nilai, serial/lot, WIP per job, outstanding PO/GR/invoice, AR/AP open item, uang muka, wallet/refund, aset/depresiasi dan payroll liability. Harga master tidak dapat merekonstruksi HPP historis yang hilang.

**MIG-03:** bila jejak biaya historis tidak tersedia, saldo opening layer harus berasal dari valuasi yang disetujui dan diberi label opening balance; jangan mengaku sudah memiliki traceability lot lama. Histori lama disediakan read-only bila tidak diimpor penuh, dengan strategi yang disetujui owner.

**MIG-04:** cutoff transaksi dan freeze sumber → backup → migrasi → rekonsiliasi → UAT saldo → persetujuan go-live. Stok/jurnal tidak boleh diposting independen di dua sistem setelah cutoff. Strategi rollback menentukan perlakuan transaksi baru sebelum mengaktifkan target.

**MIG-05:** sign-off wajib: opening trial balance seimbang; persediaan/WIP/AR/AP/kas/aset sesuai sumber yang disahkan; tidak ada duplikasi nomor dan open item. Skema lama tidak diubah maknanya diam-diam; perubahan target melalui migrasi dan pemetaan terdokumentasi.

| UAT-113 | Barang kecil diterima tanpa memilih lokasi; barang lain ditumpuk di staging melewati tenggat | Penerimaan **ditolak** selama lokasi belum ditunjuk, untuk semua jenis item tanpa kecuali; lokasi default item mengisi otomatis sehingga penerimaan cepat tetap lancar; barang di staging tetap berlokasi sah dan muncul di laporan okupansi sebagai terlambat dirapikan setelah tenggat |
| UAT-114 | Dua pemasukan barang melebihi kapasitas berat satu rak | Sistem menolak atau menandai pelanggaran kapasitas (berat/dimensi/qty) sesuai kebijakan; barang tidak diam-diam dipindah oleh sistem; petugas menerima daftar kerja perapian dan laporan REP-22 menampilkan pelanggaran kapasitas tersebut |
| UAT-115 | Admin menjelajah seluruh MOD-01–14 dan mencoba menambah, mengubah, serta menonaktifkan data di setiap modul | Setiap modul memiliki jalur CRUD penuh atas data miliknya tanpa bantuan vendor; penghapusan menonaktifkan (data berhistori tetap terlacak); tidak ditemukan modul yang hanya bisa dibaca padahal datanya milik pengguna |
| UAT-116 | Pengguna mencoba menyunting jurnal posted, saldo stok, saldo cuti, atau menghapus audit event secara langsung | Tidak ada endpoint/UI edit bebas; permintaan ditolak dan diarahkan ke aksi terkontrol (void/reverse, adjust-via-count, adjust-balance + approval, atau koreksi dokumen sumber); setiap aksi menyimpan aktor, alasan, waktu, dan sumber; `/audit-events` dan `/permissions` tetap tidak dapat diubah |
| UAT-117 | Aplikasi diakses lewat domain Cloudflare dari luar bengkel | HTTPS berlaku di ujung pengguna maupun ke origin (SSL Full strict); tidak terjadi redirect loop; skema dan klien IP benar di balik proxy; hanya trafik Cloudflare yang mencapai origin |
| UAT-118 | Ekspor besar, kirim email, dan proses integrasi dijalankan pada NAS tanpa jam maintenance | Pekerjaan masuk queue dan diproses worker persisten; scheduler berjalan tiap menit; status terlihat di `/scheduler-status`; kegagalan notifikasi tidak membatalkan transaksi bisnis yang sudah sah; deploy/migrasi dapat dilakukan **tanpa mematikan layanan** dan jeda layanan tetap sesingkat yang disepakati |
| UAT-119 | NAS dimatikan total lalu dipulihkan di perangkat pengganti | Aplikasi, database dan lampiran pulih dalam RTO ≤4 jam dari backup offsite terenkripsi, bukan dari snapshot di NAS yang sama; bukti uji restore tercatat; tidak ada kehilangan data di luar RPO ≤1 jam; penggantian satu disk pada volume SHR berjalan tanpa kehilangan data dan tanpa menghentikan layanan |
| UAT-120 | Lampiran foto berukuran besar diunggah dari web dan Android | Unggahan berhasil dengan penggabungan di sisi klien bila melampaui batas proxy; berkas tersimpan di private storage dan diakses lewat signed URL; berkas tidak dapat dibuka tanpa izin walau URL ditebak |

**Definition of Done setiap requirement:** alur normal dan error selesai; permission dan audit benar; reversal/adjustment bila relevan tersedia; laporan terdampak cocok; tidak ada tombol dummy atau data simulasi; pengujian angka/concurrency yang relevan lulus; UAT pengguna berwenang tercatat; panduan operasi dan recovery tersedia. Fungsi bisnis mempunyai kontrak API dan bukti paritas web/Android; field referensi mempunyai keputusan quick add, bukan diasumsikan seluruh kolom bisa membuat record.

Sebelum release, buat matriks traceability ID requirement → layar/endpoint → aturan posting → pengujian → bukti UAT → persetujuan. Requirement tanpa bukti tidak boleh ditandai selesai. Fitur bersyarat INT-03 ditandai blocked/excluded by approval secara eksplisit, tidak dipresentasikan sebagai integrasi aktif.

## 21. Urutan implementasi tanpa mengurangi cakupan

Fase merupakan urutan ketergantungan, bukan penghapusan fitur atau janji tanggal selesai. Desain laporan, COA, dimensi dan contoh angka dimulai di fase A; bukan baru dipikirkan setelah transaksi dibuat.

| Fase | Hasil | Gerbang penerimaan |
| --- | --- | --- |
| A — Validasi bisnis dan fondasi | Kebijakan akuntansi, master, COA/dimensi, auth web/perangkat Android, RBAC, approval, audit, sequence, period lock, kontrak API, design system web dan pola quick add | Kebijakan kritis §23 disetujui; permission dan posting dasar teruji; kontrak serta pola popup lolos skenario terkait UAT-56–70 |
| B — Ledger dan pembelian/stok | Jurnal, opening balance, marketplace, PR/PO/GR/AP, wallet, FIFO, landed cost, adjustment, clearing | UAT-01–13, 20–24 yang relevan; stok dan GL cocok |
| C — CRM dan pekerjaan | Kendaraan, estimasi, quotation/SO/DP, job/BOM/routing, produksi, WIP, QC, subkontrak, change order | Job contoh dari quote sampai hasil selesai dengan biaya lengkap |
| D — Komersial dan finance lengkap | Invoice/termin, revenue/HPP, collection, tax, bank, budget, overhead, closing, garansi | UAT end-to-end revenue/cash/WIP dan closing |
| E — Pendukung dan seluruh laporan | SDM/payroll, aset/maintenance, portal, seluruh katalog laporan, integrasi tersedia | MOD-01–14 dan laporan wajib memiliki bukti UAT; rekonsiliasi menyeluruh |
| F — Migrasi dan go-live | Dry run, training, restore/load test, sign-off opening, cutover dan monitoring | Semua requirement wajib diterima; tidak ada gap finansial kritis; rencana recovery teruji |

Tidak boleh menyebut produk “full fitur selesai” hanya karena fase awal hidup. Modul yang memengaruhi laba, izin, atau saldo tidak dapat dinyatakan selesai hanya berdasarkan tampilan menu.

## 23. Keputusan yang perlu disahkan sebelum implementasi terkait

PRD tetap dapat digunakan untuk diskusi dan estimasi. Hal-hal berikut tidak boleh ditebak saat konfigurasi produksi:

**Sudah ditetapkan owner:** pelanggan Umum wajib DP minimum 50%. Aturan ini tidak menunggu keputusan ambang approval atau kebijakan kredit lain. Default rancangan yang masih perlu disahkan adalah dasar grand total termasuk pajak/biaya pelanggan, gate operasional terperinci dan syarat pelunasan sisa sebagaimana SAL-09–12; tidak boleh menganggap semuanya telah dinyatakan owner.

| Keputusan | Default rancangan | Pihak pengesah / dampak |
| --- | --- | --- |
| Badan usaha, cabang dan gudang | Satu entitas legal, multi-cabang/gudang | Owner; multi-entitas menambah eliminasi/konsolidasi |
| PKP, pajak dan ketentuan payroll | Engine bertanggal; tidak menetapkan tarif tanpa validasi | Finance/konsultan; menentukan pajak recoverable, DP dan kewajiban |
| Frekuensi dan cutoff payroll | Siklus mingguan dan bulanan berjalan tanpa gaji/potongan ganda; lembur sah menunjuk satu run; jadwal utama per pekerja bertanggal efektif | Owner + HR/finance; sahkan siapa berjadwal mingguan vs bulanan, hari cutoff, jadwal bayar, pemetaan minggu ke bulan dan perlakuan lembur lewat cutoff |
| Retensi dokumen HR dan PII | Data gaji/identitas/BPJS/rekening/bukti medis disimpan dengan retensi terpisah; penghapusan hanya setelah kewajiban berlalu; legal hold mengatasi permintaan hapus | Owner + HR/finance/legal; sahkan masa simpan per jenis dokumen, dasar hukum, dan siapa berwenang menghapus |
| Kapan revenue diakui | Acceptance untuk job custom, penyerahan kontrol untuk retail | Finance; kontrak over-time membutuhkan kebijakan tersendiri |
| Kapitalisasi dan overhead | WIP untuk biaya produksi yang memenuhi syarat; opex terpisah | Finance; tarif, driver, kapasitas normal dan variance |
| Sumber aktual biaya marketplace | Bukti order/invoice/ongkir; provisional diberi status | Purchasing + finance; voucher/cashback/refund dan tolerance |
| Ambang approval dan batas kredit | Matriks per nominal/margin/overbudget | Owner; pemisahan tugas dan pengecualian usaha kecil |
| Rincian pembayaran pelanggan | Minimum 50% pelanggan Umum sudah wajib; dasar hitung grand total dan gate mengikuti SAL-09–12 sebagai rancangan awal | Owner + finance; sahkan dasar hitung, termin sisa dan kebijakan kategori non-Umum tanpa bypass Umum |
| Jadwal kerja dan lembur | Master/roster berversi; actual vs approved terpisah; tanpa tarif hukum hardcode | HR + finance; sahkan kalender, batas jam, formula upah, approval dan alokasi premium lembur |
| Profil pelanggan dan karyawan | Field terstruktur dan validasi sesuai CUS-05–08 serta EMP-01–05 | Owner/HR/finance; sahkan tahap kelengkapan, akses sensitif, verifikasi rekening dan retensi |
| Hak cuti dan pinjaman | Kuota/accrual/carry-over berversi; pinjaman tanpa bunga sebagai default rancangan | HR + owner + finance; sahkan jenis/hak cuti, limit/tenor/potongan serta perjanjian yang berlaku |
| PR/PO, penerimaan dan pembayaran | PR berjenjang; PO sebagai komitmen; GRN satu-satunya jalur qty stok; matching tiga arah | Owner + purchasing + gudang + finance; sahkan ambang approval, toleransi match dan alur darurat |
| Termin pembayaran vendor/pelanggan | Master berversi; default COD/CBD tanpa asumsi kredit 30 hari; Net 30 berbasis tanggal invoice kecuali disahkan lain | Owner + finance; sahkan basis tanggal, hari libur, diskon pelunasan cepat dan batas kredit |
| Pengakuan utang dan piutang | Utang dari GRN (GRNI), piutang dari pengakuan penjualan; aging as-of cutoff | Finance; sahkan akun clearing, selisih kurs, dan write-off |
| Petty cash dan LPJ | Dana per custodian/cabang, transfer bukan beban, uang muka wajib dipertanggungjawabkan | Owner + finance; sahkan plafon, ambang approval, deadline LPJ dan metode imprest/non-imprest |
| Standar QC/garansi | Checklist per jenis pekerjaan, versi tersimpan; **tanda tangan digital disetujui** (setara basah) untuk inspeksi awal/akhir dan serah terima; checklist akhir ditandatangani kepala bengkel atau PLT-nya | Kepala teknis + owner; sahkan jenis/butir checklist final per pekerjaan; kewenangan tanda tangan dan format bukti digital sudah ditetapkan |
| Karo dan alat | **Karo gratis sampai alat kembali**; penggantian/perbaikan karo tidak ditagih selama alat belum check-out; alat tertahan di karo; nomor `KRO-` | Owner + kepala bengkel; sahkan bentuk unit penampung yang dipakai operasional, kebijakan biaya setelah check-out, dan siapa berwenang memindahkan alat |

| CRUD seluruh modul | **Setiap MOD-01–14 CRUD penuh atas data miliknya** (hapus = nonaktifkan); data turunan (jurnal, saldo stok, layer, GRNI, entri biaya, ringkasan absensi, saldo cuti, payslip/ledger, register aset, approval task, akses portal) hanya berubah lewat **aksi terkontrol** berizin + beralasan + berjejak; `/permissions` dan `/audit-events` sengaja tetap tidak dapat diubah | Owner + tim teknis; sahkan siapa berwenang atas tiap aksi turunan (void jurnal, adjust-balance, write-off pinjaman), dan konfirmasi pengecualian `/permissions` + `/audit-events` |

| Platform/provider integrasi | Manual/impor wajib, API hanya resmi | Owner + provider; izin, biaya dan ketersediaan API |
| API, web dan Android | API-first Laravel, web React/TypeScript dengan stack/komponen wajib §17.6; Android sebagai konsumen kontrak; online-first | Tim teknis + owner; sahkan distribusi aplikasi Android, masa berlaku token/perangkat dan dukungan versi klien; kewajiban cmdk/Combobox bukan opsi yang menunggu persetujuan ulang |

| Volume dan infrastruktur | Target awal NFR-02–07 | Owner + tim teknis; sizing, backup dan SLA |
